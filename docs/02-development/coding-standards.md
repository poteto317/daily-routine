# React（Next.js）コーディング規約

このプロジェクトのReact/Next.js開発における設計ルールです。フロントエンドアーキテクトとして、以下の5つのディレクトリ分類と依存関係ルールを厳守してください。

## 1. ディレクトリの分類と責務

### ① layouts/ (配置・枠組み)

- アプリの「外殻」を定義する。
- ヘッダー、サイドバー、フッターなどの全体的な配置（Grid/Flex）のみを管理する。
- ページをまたいで維持される構造を担当し、特定のビジネスロジックは持たない。

### ② app/ (または pages/) (組み立て・ルーティング)

- 実際のURLに対応するエントリーポイント。
- 役割は「各要素の結合」のみ。layoutsの中にfeaturesを配置し、画面を完成させる。

### ③ features/ (ドメイン・機能単位)

- ビジネスロジックを伴う「機能」の塊（例：auth, search, cart, profile）。
- フォルダ内に、その機能専用の「UIコンポーネント」「カスタムフック」「型定義」「API呼出」を閉じ込める（Co-location）。
- 外部への公開は、フォルダ直下の `index.ts` を通じて行うこと。

### ④ components/ (共通UI部品)

- アプリ全体で使い回す、純粋なUIパーツ（Button, Input, Card, Typographyなど）。
- 特定のドメイン知識やAPI通信を持たず、Propsのみで動作する「ピュア」なコンポーネントにする。

### ⑤ hooks/ (共通ロジック)

- 汎用的なカスタムフック（useWindowSize, useLocalStorage, useDebounceなど）。
- 特定の機能（Feature）に依存しない、純粋なユーティリティロジックのみ。

---

## 2. 依存関係（重要ルール）

コードの複雑化を防ぐため、以下の「単方向の依存ルール」を徹底してください。

- **app** は、layouts, features, components, hooks のすべてを参照できる。
- **features** は、components, hooks を参照できる。
- **layouts** は、components, hooks を参照できる。
- **components と hooks** は、layouts, features, app のどれも参照してはならない（独立性を保つ）。

## 3. コーディングスタイル

### コメントは日本語で記述

- 関数・クラス・複雑なロジックには日本語でコメントを付ける
- JSDocコメントも日本語推奨
- 例: `/** ルーティンの完了状態を切り替える */`

### フォーム・キーボード操作の原則

- **IME 変換中の Enter 誤爆防止**: 日本語入力（IME変換確定）での Enter キー押下によってフォーム送信やリスト追加が誤発火しないよう、`keydown` イベントハンドラでは必ず `isImeComposingKeyDown`（`src/lib/isImeComposingKeyDown.ts`）で判定を行ってください。
  ```typescript
  if (isImeComposingKeyDown(e)) return;
  ```
- **Escape キーのモーダル閉じ (`useCloseOnEscape`)**: `role="dialog"` / `aria-modal="true"` を持つモーダルやパネルでは、共通フック `useCloseOnEscape`（`src/hooks/useCloseOnEscape.ts`）を使用してください。内部で `isImeComposingNativeKeyDown` により IME 変換キャンセル時の誤クローズを防ぎます。
- **作成フォーム送信時のソフトウェアキーボード自動収納 (`useDismissKeyboardOnSubmit`)**: モバイル端末でアイテム作成後にソフトウェアキーボードが開いたまま残るのを防ぐため、作成フォームの送信ハンドラには `useDismissKeyboardOnSubmit`（`src/hooks/useDismissKeyboardOnSubmit.ts`）を使用してください。`onSubmit` によるアンマウントより先にアクティブな入力要素を `blur()` します。

### React Compiler と今日・現在時刻

このプロジェクトは React Compiler（`next.config.ts` の `reactCompiler: true`）で、フック・コンポーネントを自動でメモ化します。props・state・フックの戻り値に依存しない式は最初の描画の値が使い回されるため、本体で求めた「今日」「現在時刻」は、画面を開き直すまで最初の描画の値に固定されます。Jest（ts-jest）はコンパイラを通さないので、単体テストでは検出できません。

- **描画時に「今日」「現在時刻」を求めない**: フック・コンポーネントの本体で `new Date()`・`getTodayString()` などを呼ばないでください。保存する日付に使う値は特に、イベントハンドラの中（呼ばれた時点）で取ってください。描画時に取った値をハンドラに持たせると、再描画の無いまま 0 時をまたいだ操作が前日で処理されます。
- **描画時に今日が必要なとき**は `src/hooks/useToday.ts` のフック（`useJstTodayKey`・`useJstDay`・`useLocalTodayKey`）を使ってください。各フックは `"use no memo"` で自動メモ化から外してあり、呼ぶ側は戻り値を依存として扱うので、日をまたいだ後の次の描画で新しい今日になります（0 時に自動で再描画はしません）。`useMemo` で使うときは、戻り値を計算の中で実際に使ってください（依存の配列に足すだけでは、コンパイラが依存から外します）。
- **描画時に現在時刻が必要なとき**は `src/hooks/useCurrentMinute.ts` の `useCurrentMinute()` を使ってください。戻り値は、いまの「分」の開始時刻（epoch ミリ秒）です。現在時刻で判定する関数は、中で時計を読まずに、時刻を引数で受け取る純粋な関数にし、フックの戻り値を渡してください（例: `isRoutinePast(routine, nowMs)`）。関数の中で時計を読むと、コンパイラのメモ化のキーに時刻が入らず、判定が最初の描画の値に固定されます（#9）。毎分のタイマーはありません。現在時刻を読み直させたいとき（アプリがバックグラウンドから戻ったときなど）は `notifyCurrentMinute()` を呼んでください。分が変わっていれば、フックを使うコンポーネントが再描画されます（ルーティンでは `useRoutineForegroundSync` が、復帰時とフォールバックタイマーの回に呼びます）。ただし、サーバーで描画されるコンポーネントや、ハイドレーションの最初の描画で描かれるコンポーネントでは使わないでください（サーバーとクライアントで分がずれると、ハイドレーションの不一致になります）。いまの利用箇所は、最初の描画でローディングを返す `AuthGuard` の内側だけです。
- **機能側の関数（祝日の判定など）を描画のたびに呼ぶ必要があるとき**は、共通フックでは書けない（`src/hooks/` は `src/features/` を参照しない）ので、機能側に本体の最初の文が `"use no memo"` の関数を置いてかまいません（例: `src/features/routine/hooks/useHomeViewDateState.ts`）。その関数は、契約テストの `USE_NO_MEMO_TARGETS` に足してください。
- **新しく今日・現在時刻を使うフック・コンポーネントを直したら**、契約テスト `src/__tests__/reactCompilerToday.contract.test.ts` の `TODAY_TARGETS` に足してください。コンパイル結果で、今日・現在時刻が固定されていないことを確かめます。
- **対象外**: イベントハンドラの中、`useState` の初期化関数の中で取る今日は対象外です（描画のたびに求める値ではありません）。ただし、`useState` の初期化で取る今日を画面に出す今日（日付のラベル・祝日・既定の選択）に使うと、日をまたいでも古いまま残ります（#210）。表示に使う今日は描画のたびに求めてください。

### React Compiler と保存された設定の値

保存された設定（`getSettings()`）は、props・state・フックの戻り値のどれにも依存しないので、フック・コンポーネントの本体で読んで表示に使うと、React Compiler が最初の描画の値に固定します（書き方によっては、ほかの props などに依存するメモ化のブロックの中に入り、その値が変わるまで古い値のままになります）。Jest は React Compiler を通さないので、単体テストでは検出できません（「React Compiler と今日・現在時刻」と同じ仕組みです）。次の規約に従ってください。

- **購読するフックで受け取る**: 表示に使う設定は、設定を購読するフックで受け取ってください。スワイプの動作は `useSwipeActionSetting()`（`src/features/settings/state/useSwipeActionSetting.ts`）を使います。
- **関数の中でも読まない**: 本体から呼ぶ関数が、呼ばれた時点（描画中）に `getSettings()` を読み、その結果を表示に使う場合も、同じように固定されます（関数に包んでも、設定の値はコンパイラのメモ化のキーに入りません）。表示に使う設定を扱う関数は、中で設定を読まずに、設定の値を引数で受け取る関数にし、購読するフックの戻り値を渡してください。
- **ほかの項目が要るとき**: 同じ形のフックを足してください。スナップショットは、文字列・数値・真偽値か、変わらない限り同じ参照の値にします（`getSettings()` は、保存データがあると呼ぶたびに新しいオブジェクトを返すので、設定の全体をスナップショットにしません）。配列・オブジェクトの項目も、保存データがあると、読むたびに新しい参照になります。そのまま返すと再描画が止まらなくなるので、中身が前回と同じなら、前回返した値を返してください。保存データは値の型を検証していないので、スナップショットでは、受け付ける値のどれかに直してから返します（壊れた値がオブジェクトや配列だと、読むたびに参照が変わり、再描画が止まらなくなります）。受け付ける値の一覧は、項目の型をキーにしたオブジェクトで持ち、値を足したときに型エラーで気付けるようにしてください（例: `useSwipeActionSetting.ts` の `SWIPE_ACTIONS`）。
- **サーバー側のスナップショット**: `DEFAULT_SETTINGS` の値にします（保存された値を読むと、ハイドレーションの不一致になります）。サーバーでの描画とハイドレーションの最初の描画は既定値になり、その後で保存された値に切り替わるので、見た目が大きく変わる設定を、サーバーで描画されるコンポーネントで使うときは、切り替わりが見えることに注意してください（いまの利用箇所は、最初の描画でローディングを返す `AuthGuard` の内側だけです）。
- **契約テストに足す**: フックを使うフック・コンポーネントは、契約テスト（`src/__tests__/reactCompilerSettings.contract.test.ts`）の `SETTINGS_TARGETS` に足してください。
  - `name` に書く名前: フックの戻り値は、名前のある変数に入れて使い、その変数名を `dependencies` の `name` に書きます（変数に入れずに使うと、比較は、コンパイラが付けた名前（`t0` など）との比較になり、`name` に書ける名前がありません）。
  - `comparisons` に書く件数: `dependencies` の `comparisons` には、コンパイル結果の `$[n] !== 変数名` の件数を書きます。フックの戻り値を直接の依存に持つメモ化のブロックの数で、値を使う箇所の数とは限りません。同じブロックの中で何度使っても 1 件です。式の形によっては、値を使っていても数に入りません。
    - 数に入る例: 値をそのまま JSX に渡す箇所、import した関数の結果をそのまま描画に使う箇所。
    - 数に入らない例: 比較の結果で文字列を選ぶ箇所、`String()` などの変換に渡す箇所、ほかのフックの引数に渡す箇所。
    - 似た形でも結果が変わることがあるので、形から推測せず、契約テストを実行して、実際の件数を確かめてください。
  - `comparisons` は 1 以上にする: 0 件では、件数の確認が何も守らないので、契約テストで落ちます。実際の件数が 0 件になるときは、値をそのまま JSX に渡すなど、件数に入る形で使う箇所を作ってください。
  - 件数を直すとき: 設定の値を使う箇所を増やした・減らしたときと、値を使う式の形を変えたときは、件数が変わることがあります。どの箇所もフックの戻り値から求めていることを確かめてから、この件数を直してください。
- **契約テストで守られる範囲**: 契約テストが確かめるのは、`SETTINGS_TARGETS` に載せたファイルだけです。
  - ファイルごとに確かめること:
    - ソースに `getSettings` が書かれていない。本体で読む形と、同じファイルの中の関数に包んで読む形が、ここで落ちます。文字で探すので、コメントに書いた場合も落ちます。イベントの時点で読む設定や、`useState` の初期値として読む設定（フォームの初期値など、その後は利用者が編集する値）が要るときも、このファイルには書けないので、読む処理を、コンポーネント・フック以外のファイルの関数に置いてください（置き方は、下の「対象外」に書いています）。
    - コンパイル結果の「最初の描画で 1 回だけ実行されるブロック」に、`getSettings(` が無い。
    - フックの戻り値を直接の依存に持つメモ化のブロックの数が、`comparisons` と同じである（`comparisons` を 1 以上で書いていることも確かめます）。フックの戻り値を直接の依存に持っていたブロックが依存から外れると、件数が減って落ちます。フックの戻り値を渡していた箇所を、ほかのファイルの関数（中で `getSettings()` を読む）の呼び出しに置き換えた場合が、これに当たります（別々のブロックにある箇所の一部だけを置き換えた場合も落ちます。置き換えても件数が変わらない場合は、下の「レビューで確かめること」に書いています）。
  - 契約テストでは見つからないので、レビューで確かめること:
    - 一覧に無いファイル。
    - ほかのファイルの関数（中で `getSettings()` を読む）を本体から呼ぶ形のうち、件数が変わらないもの。呼び出しを新しく足しただけの場合、同じメモ化のブロックの中にある複数の箇所（例: 同じ JSX 要素の 2 つの属性）の一部だけを置き換えた場合（残りの箇所の比較が 1 件残ります）、もともと件数に入っていない箇所を置き換えた場合（例: 比較の結果で文字列を選ぶ箇所、`String()` などの変換に渡す箇所、ほかのフックの引数に渡す箇所）が、これに当たります。
- **対象外**: 対象外になる読み方、`SETTINGS_TARGETS` に載せたファイルでその読み方が要るときの置き方、対象外にならない読み方は、次のとおりです。
  - 対象外の読み方（次の 2 つ）:
    - イベントハンドラの中で読む設定（イベントの時点で読む）。
    - `useState` の初期値として読む設定（最初の 1 回だけ読み、その後は、利用者が編集する値として state で持つもの。フォームの初期値がこれに当たります。例: `src/features/settings/state/useSettingsFormState.ts` の `useState(createInitialSettingsFormState)`。`SETTINGS_TARGETS` に載せていないファイルなので、同じファイルの中の関数で読んでいます）。
  - `SETTINGS_TARGETS` に載せたファイルで、これらの読み方が要るとき: `SETTINGS_TARGETS` に載せたファイルでは、これらの読み方も、契約テストの「ソースに `getSettings` が書かれていない」で落ちます。読む処理を、コンポーネント・フック以外のファイルの関数に置き、その関数が設定を読むのが、イベントの時点か、`useState` の初期化のときだけになるようにしてください。
    - イベントの時点で読む例: `src/features/routine/helpersPresentation.ts` の `createSwipeHandler` は、本体から呼びますが、設定を読むのは、返したハンドラが呼ばれた時点です。
    - 初期値として読む例: `useState(() => readX())`。
  - 対象外にならない読み方:
    - 上の「対象外の読み方」の 2 つ以外の、描画中に読んだ値を表示に使う形（上の「関数の中でも読まない」）。
    - `useState` の初期値として読む形でも、利用者が編集しない表示（カードの見た目など）に使う設定。固定の仕組みは違いますが（React Compiler ではなく、state が最初の値を持ち続ける）、設定を変えても、コンポーネントが作り直されるまで古いまま残ります。表示に使う設定は、購読するフックで受け取ってください。

### ダークモードの配色

ダークモードでも、`CardPanel` など背景が明るいカード（`dark:bg-slate-100` など）があります。背景の明るさと文字色の組み合わせを間違えると、文字が読めなくなります。

- **背景に合わせて文字色を決める**（レビューで確認）: ダークモードでも背景が明るい場所は暗い文字、暗い背景の上は明るい文字にしてください。
  - ダークモードでも明るい背景の例: `CardPanel`、ヘッダーメニューのパネル、ルーティンのフォーム、設定・管理画面の行（`dark:bg-gray-200`）
  - 暗い背景の例: Todo アイテム、Todo のメニュー、プリセットのカード
- **コントラスト比を満たす**（レビューで確認）: 通常の文字は背景とのコントラスト比 4.5:1 以上、アイコン・記号は 3:1 以上にしてください。
- **半透明の暗い背景を使わない**（契約テストで自動検出）: `dark:bg-red-900/20` のような半透明の暗い背景を明るいカードに重ねると、中間色になってどちらの文字も読めません。背景は不透明にしてください（明るいカードの上は不透明の明るい色、暗いメニューの上は `dark:hover:bg-red-900` のような不透明の暗い色。その上の文字も明るくする）。契約テスト `src/__tests__/darkModeContrast.contract.test.ts` が、`dark:` の変種（`dark:hover:` など）、`black`、600〜950 番台、任意値の透明度（`/[0.2]`）を含めて禁止しています。背景が必ず暗い場所だけの正当な例外は、テスト内の `ALLOWED` に理由付きで足してください。
- **同じ要素で `dark:` の背景を条件で上書きしない**（レビューで確認。個別の部品はそれぞれのテストで固定）: `dark:bg-white` を共通部分に置いて、条件のときだけ `dark:bg-red-100` を足しても、同じ詳細度のクラスは Tailwind の CSS の出力順で決まるため、足した色が効きません。背景のクラスは条件の分岐の中に置き、どちらか 1 つだけが付くようにしてください。
- **明暗の両方で使う共通部品は、色調を props で切り替える**（レビューで確認。型で必須にして防ぐ）: 置かれる背景の明るさで色が変わる部品（例: `TodoItemDragHandle` の `tone`）は、props で色調を切り替え、必須にしてください。既定値を置くと、指定し忘れた呼び出し側が静かに読めなくなります。

### ViewModelパターンの適用

- **テキスト定数**: `locales/ja.json` にまとめる（国際化対応）
- **ビジネスロジック**: `helpers.ts` に関数として抽出
- **UIコンポーネント**: 状態管理とロジック呼び出しのみ

### ファイル配置の原則

- 各機能（feature）フォルダに `locales/ja.json` を配置
- コンポーネントは `components/` 配下に配置
- 共通処理は `helpers.ts` に集約

## 4. コードレビューの観点

- コードを生成する際は、どのフォルダにどのファイルを配置すべきかを明示してください。
- 常に「変更のしやすさ」と「削除のしやすさ」を意識した疎結合なコードを作成してください。
- コメントが日本語で書かれているか確認してください。
- テキスト定数がハードコードされていないか確認してください。
- フォーム入力やキーボード操作で IME 確定が考慮されているか確認してください。
- フック・コンポーネントの本体で「今日」「現在時刻」を求めていないか、現在時刻で判定する関数が中で時計を読んでいないか（`useCurrentMinute()` の値を引数で渡す）、`useState` の初期化で取った今日を画面に出す今日（日付のラベル・祝日・既定の選択）に使っていないか確認してください（前の 2 つは React Compiler で固定され、最後は日をまたいでも古いまま残る。「React Compiler と今日・現在時刻」）。
- フック・コンポーネントの本体で `getSettings()` を呼び、その値を表示に使っていないか、本体から呼ぶ関数が、描画中に `getSettings()` を読んで、その結果を表示に使っていないか、`useState` の初期値として読んだ設定を、利用者が編集しない表示に使っていないか確認してください（前の 2 つは React Compiler で最初の描画の値に固定され、最後は設定を変えても、コンポーネントが作り直されるまで古いまま残る。購読するフックを使い、関数には値を引数で渡す。イベントの時点で読む設定と、`useState` の初期値として読み、その後は利用者が編集する設定（フォームの初期値）は対象外。「React Compiler と保存された設定の値」）。
- ダークモードで、背景に合った文字色になっているか、半透明の暗い背景や `dark:` の背景の条件付き上書きが無いか、明暗の両方で使う共通部品の色調が必須の props になっているか確認してください（「ダークモードの配色」）。
