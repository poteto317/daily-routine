# React（Next.js）コーディング規約

このプロジェクトのReact/Next.js開発における設計ルールです。フロントエンドアーキテクトとして、以下の5つのディレクトリ分類と依存関係ルールを厳守してください。

## 1. ディレクトリの分類と責務

### ① layouts/ (配置・枠組み)

- アプリの「外殻」を定義する。
- ヘッダー、サイドバー、フッターなどの全体的な配置（Grid/Flex）のみを管理する。
- ページをまたいで維持される構造を担当し、特定のビジネスロジックは持たない。

### ② app/ (または pages/) (組み立て・ルーティング)

- 実際のURLに対応するエントリーポイント。
- 役割は「各要素の結合」のみ。layoutsの中にfeaturesを配置し、画面を完成させる。

### ③ features/ (ドメイン・機能単位)

- ビジネスロジックを伴う「機能」の塊（例：auth, search, cart, profile）。
- フォルダ内に、その機能専用の「UIコンポーネント」「カスタムフック」「型定義」「API呼出」を閉じ込める（Co-location）。
- 外部への公開は、フォルダ直下の `index.ts` を通じて行うこと。

### ④ components/ (共通UI部品)

- アプリ全体で使い回す、純粋なUIパーツ（Button, Input, Card, Typographyなど）。
- 特定のドメイン知識やAPI通信を持たず、Propsのみで動作する「ピュア」なコンポーネントにする。

### ⑤ hooks/ (共通ロジック)

- 汎用的なカスタムフック（useWindowSize, useLocalStorage, useDebounceなど）。
- 特定の機能（Feature）に依存しない、純粋なユーティリティロジックのみ。

---

## 2. 依存関係（重要ルール）

コードの複雑化を防ぐため、以下の「単方向の依存ルール」を徹底してください。

- **app** は、layouts, features, components, hooks のすべてを参照できる。
- **features** は、components, hooks を参照できる。
- **layouts** は、components, hooks を参照できる。
- **components と hooks** は、layouts, features, app のどれも参照してはならない（独立性を保つ）。

## 3. コーディングスタイル

### コメントは日本語で記述

- 関数・クラス・複雑なロジックには日本語でコメントを付ける
- JSDocコメントも日本語推奨
- 例: `/** ルーティンの完了状態を切り替える */`

### フォーム・キーボード操作の原則

- **IME 変換中の Enter 誤爆防止**: 日本語入力（IME変換確定）での Enter キー押下によってフォーム送信やリスト追加が誤発火しないよう、`keydown` イベントハンドラでは必ず `isImeComposingKeyDown`（`src/lib/isImeComposingKeyDown.ts`）で判定を行ってください。
  ```typescript
  if (isImeComposingKeyDown(e)) return;
  ```
- **Escape キーのモーダル閉じ (`useCloseOnEscape`)**: `role="dialog"` / `aria-modal="true"` を持つモーダルやパネルでは、共通フック `useCloseOnEscape`（`src/hooks/useCloseOnEscape.ts`）を使用してください。内部で `isImeComposingNativeKeyDown` により IME 変換キャンセル時の誤クローズを防ぎます。
- **作成フォーム送信時のソフトウェアキーボード自動収納 (`useDismissKeyboardOnSubmit`)**: モバイル端末でアイテム作成後にソフトウェアキーボードが開いたまま残るのを防ぐため、作成フォームの送信ハンドラには `useDismissKeyboardOnSubmit`（`src/hooks/useDismissKeyboardOnSubmit.ts`）を使用してください。`onSubmit` によるアンマウントより先にアクティブな入力要素を `blur()` します。

### React Compiler と今日・現在時刻

このプロジェクトは React Compiler（`next.config.ts` の `reactCompiler: true`）で、フック・コンポーネントを自動でメモ化します。props・state・フックの戻り値に依存しない式は最初の描画の値が使い回されるため、本体で求めた「今日」「現在時刻」は、画面を開き直すまで最初の描画の値に固定されます。Jest（ts-jest）はコンパイラを通さないので、単体テストでは検出できません。

- **描画時に「今日」「現在時刻」を求めない**: フック・コンポーネントの本体で `new Date()`・`getTodayString()` などを呼ばないでください。保存する日付に使う値は特に、イベントハンドラの中（呼ばれた時点）で取ってください。描画時に取った値をハンドラに持たせると、再描画の無いまま 0 時をまたいだ操作が前日で処理されます。
- **描画時に今日が必要なとき**は `src/hooks/useToday.ts` のフック（`useJstTodayKey`・`useJstDay`・`useLocalTodayKey`）を使ってください。各フックは `"use no memo"` で自動メモ化から外してあり、呼ぶ側は戻り値を依存として扱うので、日をまたいだ後の次の描画で新しい今日になります（0 時に自動で再描画はしません）。`useMemo` で使うときは、戻り値を計算の中で実際に使ってください（依存の配列に足すだけでは、コンパイラが依存から外します）。
- **描画時に現在時刻が必要なとき**は `src/hooks/useCurrentMinute.ts` の `useCurrentMinute()` を使ってください。戻り値は、いまの「分」の開始時刻（epoch ミリ秒）です。現在時刻で判定する関数は、中で時計を読まずに、時刻を引数で受け取る純粋な関数にし、フックの戻り値を渡してください（例: `isRoutinePast(routine, nowMs)`）。関数の中で時計を読むと、コンパイラのメモ化のキーに時刻が入らず、判定が最初の描画の値に固定されます（#9）。毎分のタイマーはありません。現在時刻を読み直させたいとき（アプリがバックグラウンドから戻ったときなど）は `notifyCurrentMinute()` を呼んでください。分が変わっていれば、フックを使うコンポーネントが再描画されます（ルーティンでは `useRoutineForegroundSync` が、復帰時とフォールバックタイマーの回に呼びます）。
- **機能側の関数（祝日の判定など）を描画のたびに呼ぶ必要があるとき**は、共通フックでは書けない（`src/hooks/` は `src/features/` を参照しない）ので、機能側に本体の最初の文が `"use no memo"` の関数を置いてかまいません（例: `src/features/routine/hooks/useHomeViewDateState.ts`）。その関数は、契約テストの `USE_NO_MEMO_TARGETS` に足してください。
- **新しく今日・現在時刻を使うフック・コンポーネントを直したら**、契約テスト `src/__tests__/reactCompilerToday.contract.test.ts` の `TODAY_TARGETS` に足してください。コンパイル結果で、今日・現在時刻が固定されていないことを確かめます。
- **対象外**: イベントハンドラの中、`useState` の初期化関数の中で取る今日は対象外です（描画のたびに求める値ではありません）。ただし、`useState` の初期化で取る今日を画面に出す今日（日付のラベル・祝日・既定の選択）に使うと、日をまたいでも古いまま残ります（#210）。表示に使う今日は描画のたびに求めてください。

### ダークモードの配色

ダークモードでも、`CardPanel` など背景が明るいカード（`dark:bg-slate-100` など）があります。背景の明るさと文字色の組み合わせを間違えると、文字が読めなくなります。

- **背景に合わせて文字色を決める**（レビューで確認）: ダークモードでも背景が明るい場所は暗い文字、暗い背景の上は明るい文字にしてください。
  - ダークモードでも明るい背景の例: `CardPanel`、ヘッダーメニューのパネル、ルーティンのフォーム、設定・管理画面の行（`dark:bg-gray-200`）
  - 暗い背景の例: Todo アイテム、Todo のメニュー、プリセットのカード
- **コントラスト比を満たす**（レビューで確認）: 通常の文字は背景とのコントラスト比 4.5:1 以上、アイコン・記号は 3:1 以上にしてください。
- **半透明の暗い背景を使わない**（契約テストで自動検出）: `dark:bg-red-900/20` のような半透明の暗い背景を明るいカードに重ねると、中間色になってどちらの文字も読めません。背景は不透明にしてください（明るいカードの上は不透明の明るい色、暗いメニューの上は `dark:hover:bg-red-900` のような不透明の暗い色。その上の文字も明るくする）。契約テスト `src/__tests__/darkModeContrast.contract.test.ts` が、`dark:` の変種（`dark:hover:` など）、`black`、600〜950 番台、任意値の透明度（`/[0.2]`）を含めて禁止しています。背景が必ず暗い場所だけの正当な例外は、テスト内の `ALLOWED` に理由付きで足してください。
- **同じ要素で `dark:` の背景を条件で上書きしない**（レビューで確認。個別の部品はそれぞれのテストで固定）: `dark:bg-white` を共通部分に置いて、条件のときだけ `dark:bg-red-100` を足しても、同じ詳細度のクラスは Tailwind の CSS の出力順で決まるため、足した色が効きません。背景のクラスは条件の分岐の中に置き、どちらか 1 つだけが付くようにしてください。
- **明暗の両方で使う共通部品は、色調を props で切り替える**（レビューで確認。型で必須にして防ぐ）: 置かれる背景の明るさで色が変わる部品（例: `TodoItemDragHandle` の `tone`）は、props で色調を切り替え、必須にしてください。既定値を置くと、指定し忘れた呼び出し側が静かに読めなくなります。

### ViewModelパターンの適用

- **テキスト定数**: `locales/ja.json` にまとめる（国際化対応）
- **ビジネスロジック**: `helpers.ts` に関数として抽出
- **UIコンポーネント**: 状態管理とロジック呼び出しのみ

### ファイル配置の原則

- 各機能（feature）フォルダに `locales/ja.json` を配置
- コンポーネントは `components/` 配下に配置
- 共通処理は `helpers.ts` に集約

## 4. コードレビューの観点

- コードを生成する際は、どのフォルダにどのファイルを配置すべきかを明示してください。
- 常に「変更のしやすさ」と「削除のしやすさ」を意識した疎結合なコードを作成してください。
- コメントが日本語で書かれているか確認してください。
- テキスト定数がハードコードされていないか確認してください。
- フォーム入力やキーボード操作で IME 確定が考慮されているか確認してください。
- フック・コンポーネントの本体で「今日」「現在時刻」を求めていないか、現在時刻で判定する関数が中で時計を読んでいないか（`useCurrentMinute()` の値を引数で渡す）、`useState` の初期化で取った今日を画面に出す今日（日付のラベル・祝日・既定の選択）に使っていないか確認してください（前の 2 つは React Compiler で固定され、最後は日をまたいでも古いまま残る。「React Compiler と今日・現在時刻」）。
- ダークモードで、背景に合った文字色になっているか、半透明の暗い背景や `dark:` の背景の条件付き上書きが無いか、明暗の両方で使う共通部品の色調が必須の props になっているか確認してください（「ダークモードの配色」）。
