# レビュー指摘から得た教訓集

AI エージェント向け API（PR #175）の開発では、タスクごとのレビュー、最終レビュー、単一責任の観点でのレビュー、PR 上のサブエージェントによる 5 回のレビュー、Copilot の 2 回のレビュー（計 9 件）で、多くの指摘が出ました。このドキュメントは、それらを **特定の機能から切り離し、「どういうときに」「どんな問題が起きて」「なぜ起きるのか」「どう直すのか」** という汎用の形に整理したものです。

新しい機能を実装するとき、またはレビューをするときの確認項目として使ってください。巻末にチェックリストがあります。管理者権限で動く CLI や、秘密を扱うツールを作るときは、13 章を確認してください（PR #176 のレビューから）。

## 読み方

各項目は次の形で書いています。

- **どういうときに起きるか**: 問題が表に出る条件
- **何が起きるか**: 利用者・データ・運用への影響
- **原因**: なぜその問題が生まれたのか。実装時の考え方のどこに穴があったか
- **修正内容（汎用）**: 他の場面にも使える直し方
- **予防**: 実装・レビュー時に確認する点
- **この PR での例**: 具体的な場所とコミット

重大度の目安は次のとおりです。

| 区分 | 意味                                               |
| ---- | -------------------------------------------------- |
| 高   | データの消失・デプロイ不能・セキュリティに直結する |
| 中   | 誤動作や誤解を招くが、データは守られる             |
| 低   | 保守性・分かりやすさ・テストの強さの問題           |

## 1. 入力の扱い

外部から来る値（HTTP のパス・クエリ・ヘッダー・本文）は、**検証に失敗したら必ず明示的に拒否する（fail-closed）** のが原則です。「分からない値は無視して続行する」実装（fail-open）が、この章の問題の共通の原因でした。

### 1-1. 不正な入力が例外のまま 500 になる

- **重大度**: 中
- **どういうときに起きるか**: URL のパスに不正なパーセントエンコード（例: `DELETE /budget/expenses/%E0%A4%A`）が含まれているとき。
- **何が起きるか**: クライアントの入力ミスなのに、サーバーの内部エラー（500）として扱われます。利用者（特に AI エージェント）は「リクエストが悪い」のか「サーバーが壊れている」のか区別できず、再試行を繰り返したり、誤った対処をしたりします。ログにも不要なエラーが出ます。
- **原因**:
  1. `decodeURIComponent` は、不正なエンコードに対して `URIError` を投げます。これは、アプリケーション独自のエラー型（`ApiError`）ではない、素の例外です。
  2. 最上位のハンドラは、「独自のエラー型は 4xx として返し、それ以外の例外は想定外として 500 を返す（詳細はログにだけ出す）」という作りでした。この作りは、内部の詳細を利用者に漏らさないために正しい設計です。
  3. その結果、「入力が原因で投げられた素の例外」は、すべて「想定外のサーバーエラー」に分類されてしまいました。つまり、**入力を扱う標準関数が例外を投げうることを、ルーターを書く時点で考慮していなかった**ことが原因です。
- **修正内容（汎用）**: 外部入力に対して例外を投げうる関数（`decodeURIComponent`、`JSON.parse`、`new URL`、`new Date` など）は、呼び出し箇所で `try/catch` し、**クライアントエラーとして扱うドメインのエラーに変換する**。
- **予防**: 外部入力を直接渡している標準関数を洗い出し、「それが投げる例外はどう処理されるか」を確認する。ハンドラのエラー分類（4xx と 5xx の境目）を、設計時に明文化する。
- **この PR での例**: `router.ts`（`c051fd4`）。400 `invalid_path` を返すようにし、テストを追加。

### 1-2. 重複・未知のクエリパラメータが黙って無視され、全件が返る

- **重大度**: 中
- **どういうときに起きるか**: `?month=2026-10&month=2026-11`（同じキーの重複）や、`?mont=2026-10`（打ち間違い）のように、**認識できないクエリ**が付いたとき。
- **何が起きるか**: 絞り込んだつもりのリクエストが、**絞り込みなしの全件取得**として成功（200）します。人間なら結果の多さで気づきますが、AI エージェントは気づかずに、全件を「その月の結果」として扱ってしまいます。
- **原因**:
  1. Express のクエリパーサーは、同じキーが複数あると値を配列にし、`a[b]=1` の形式ではオブジェクトにします。つまり、値は「文字列」とは限りません。
  2. クエリを文字列の辞書に変換する補助関数が、「文字列以外は `undefined`（指定なし）にする」実装でした。**検証ではなく、黙って捨てる変換**です。
  3. 各操作は、自分が知っているキー（`month`、`date`）だけを読みます。知らないキーは誰も見ないので、打ち間違いは誰にも検出されません。
  4. 一方、リクエスト**本文**の未知キーは、別の仕組みで 400 にしていました。つまり、「本文は厳格、クエリは寛容」という**方針の不一致**がありました。
  5. 「指定がない場合は全件」という仕様自体は妥当です。問題は、「指定したつもりなのに指定がない扱いになる」経路があったことです。
- **修正内容（汎用）**:
  - 型が想定外の値（配列・オブジェクト）は、変換で捨てずに 400 にする。
  - ルートごとに**許可するキーの一覧（許可リスト）**を持ち、それ以外のキーは、データに触れる前に 400 にする。
  - 「絞り込みの指定が無い場合に全件を返す」エンドポイントでは、特に厳格にする。
- **予防**: 「本文・クエリ・ヘッダー・パス」の検証方針を揃える。「無視してよい入力」と「拒否すべき入力」を意識的に区別する。許可リストと、操作が実際に読むキーが食い違わないよう、一覧の定義をテストで固定する。
- **この PR での例**: `requestQuery.ts`（重複・ネストを 400）と `validation/queryParams.ts`、`operations/index.ts` の許可リスト（`35b2b42`）。

### 1-3. 日付検証が一部の範囲で誤る（`Date.UTC` の年補正）

- **重大度**: 低（実害は誤拒否のみ）
- **どういうときに起きるか**: 西暦 100 年未満（例: `0050-01-01`）の日付を検証するとき。
- **何が起きるか**: 形式が正しく実在する日付なのに、「実在しない日付」として拒否されます。
- **原因**:
  1. 日付の実在確認は、`Date.UTC(year, month - 1, day)` で日付を作り、年月日が元の値と一致するかを見る方法で書いていました。
  2. JavaScript の `Date.UTC` は、**年が 0〜99 のときは 1900〜1999 年として解釈する**という仕様があります。そのため `0050` が `1950` になり、「年が一致しない」と判定されました。
  3. 境界値（閏日、100 年未満）を、最初のテストが持っていなかったため、発見が遅れました。リファクタリング時に境界値のテストを追加して初めて発覚しました。
- **修正内容（汎用）**: 年を `setUTCFullYear` で直接設定する（この補正が入らない）。日付・時刻の検証では、閏日（2/29）、月末（4/31）、年の下限・上限、0 埋めの有無をテストする。
- **予防**: 標準の日付 API の癖（補正・タイムゾーン）を把握した上で、境界値のテストを最初から書く。
- **この PR での例**: `validation/dateFormats.ts`（`18057c8`）。

### 1-4. HTTP の仕様の細部（スキーム名の大文字小文字）

- **重大度**: 低
- **どういうときに起きるか**: クライアントが `authorization: bearer <キー>`（小文字）で送ってきたとき。
- **何が起きるか**: 正しいキーなのに 401 になります。
- **原因**: `Bearer` という文字列を、**大文字小文字を区別して**比較していました。RFC 7235 では、認証スキーム名は大文字小文字を区別しないと定められています。実装時に「例では `Bearer` と書かれている」ことを根拠に、仕様を確認せずに完全一致にしました。
- **修正内容（汎用）**: 仕様に基づいて比較方法を決める（スキーム名は大文字小文字を無視、トークン部分は厳密）。余分な空白の扱い（受け付けない）も、テストで固定する。
- **予防**: プロトコルの仕様（RFC）で「区別するもの」と「区別しないもの」を確認する。
- **この PR での例**: `bearerToken.ts`（`18057c8`）。

## 2. データの整合（同期・欠損・順序）

### 2-1. 「無い」と「空」を同一視して書き込み、既存の保護をすり抜ける

- **重大度**: 高（データの消失につながる）
- **どういうときに起きるか**: 古いバージョンのアプリが最後にアップロードした同期データに、新しい機能のフィールド（例: 収入項目の配列）が**そもそも存在しない**状態で、新しいコード（API）が、そのフィールドへ書き込むとき。
- **何が起きるか**: API が、存在しなかったフィールドを 1 件だけの配列として**新しく作ります**。その後、別の端末がダウンロードすると、その端末に元々あった項目が、API が作った 1 件で**置き換わって消えます**。
- **原因（詳細）**:
  1. アプリの同期には、「**リモートにフィールドが無いときは、端末のデータを保つ**」という保護があります。これは、古いバージョンのアプリがアップロードしたデータで、新しい機能のデータが消えないようにするための、過去の不具合修正から入った重要な仕組みです。判定は `data.x ?? ローカルの値` で、`undefined` と `null` の両方を「無い」とみなします。
  2. API の読み取り用の補助関数（`readArray`、`readObject`）は、フィールドが無いとき**空の配列・オブジェクトを返す**実装でした。一覧表示では「無い＝空」と扱って問題ないため、この実装は読み取りには合理的です。
  3. ところが、作成・更新の操作は、同じ補助関数で「現在の配列」を取得し、それに 1 件を足して**書き戻します**。「無い」ものが「空」として読まれ、**「有る」状態として書かれます**。ここで、アプリ側の保護の前提（「無い」と「空」は別）が壊れます。
  4. 根本の原因は、**読み取り用に便利な既定値（空）を、書き込みの経路にもそのまま再利用した**ことです。「読む」と「書く」では、欠損の意味が違います。さらに、API が他システム（アプリ）の暗黙の前提（欠損の保護）に依存していることを、設計時に洗い出せていませんでした。
  5. 現行のアプリは、全フィールドを毎回書き込むため、通常は起きません。発生するのは、古いアプリが最後にアップロードしたときだけで、頻度は低いが、起きると**ローカルデータが失われる**ため、重大です。
- **修正内容（汎用）**:
  - 書き込み操作の対象フィールドが、**既存データに存在しない場合は、書かずに明示的なエラー（409）で拒否する**。「更新してから再試行する」ことを、メッセージで案内する。
  - 欠損の判定は、連携先の判定と**完全に同じ意味**にする（`undefined` と `null` は欠損、空配列・空オブジェクト・0・空文字・false は存在）。
  - 判定は、**入力の検証（400）の後、書き込みの前**に、トランザクション内で行う。読み取り（一覧）は、空として返してよい。更新・削除は、対象が無いので 404 のままでよい。
  - 挙動を、API リファレンスに明記する（一覧は空、更新・削除は 404 など）。
- **予防**: 他のシステムが「暗黙に守っている不変条件」を、設計時に洗い出す。「読み取り用の既定値」を「書き込み」に使い回していないか確認する。「欠損」「null」「空」の 3 つを区別してテストする。
- **この PR での例**: `syncWriter.ts` の `applyChanges` と `syncDoc.ts` の `findMissingFields`（`05b791c`）。

### 2-2. オブジェクトのキーの順序に依存した出力

- **重大度**: 低
- **どういうときに起きるか**: 「月ごとのバケット」を持つオブジェクトから、月を指定せずに全件を連結して返すとき。
- **何が起きるか**: ドキュメントには「月の順に返す」と書いてあるのに、実際の順序は保存されたキーの順序に依存し、保証されません。
- **原因**:
  1. `Object.values(map).flat()` の順序は、JavaScript の仕様上、整数に見えるキーは昇順、それ以外は**挿入順**です。`"2026-10"` のようなキーは整数ではないので、挿入順になります。
  2. 保存先（Firestore のマップ）が返すキーの順序も、保証された仕様ではありません。
  3. 実際には、たまたま昇順で返ることが多いため、テストでも気づきませんでした。「たまたま動く」順序を、仕様として文書化したことが原因です。
- **修正内容（汎用）**: 順序を約束するなら、**明示的にソートする**（キーを `sort()` してから連結する）。順序が保存順に依存する入力でテストする（キーを逆順に入れても、約束した順序で返ること）。
- **予防**: ドキュメントに順序を書くときは、「その順序を保証するコードがどこか」を確認する。オブジェクトのキー順に頼らない。
- **この PR での例**: `operations/expenses/expenseStore.ts` の `listExpenses`（`18057c8`）。

### 2-3. データの置き場所（バケットのキー）と、データ自身の値が食い違う

- **重大度**: 低
- **どういうときに起きるか**: 日付ごとのバケット（`journalHistory["2026-10-01"]`）の中のエントリが、**自分の `date` と異なるキーに入っている**（手動編集、過去のバグ、移行の途中など）とき。
- **何が起きるか**: エントリ自身の `date` でバケットを引くと、見つからずに例外になったり、何も変更されないまま成功を返したりします。
- **原因**: 更新・削除が、「エントリを見つけたバケットのキー」ではなく、「エントリ自身の `date` フィールド」でバケットを特定していました。**同じ情報が 2 か所（キーと値）にあるとき、どちらを正とするかを決めていなかった**ことが原因です。アプリ側は、全バケットを走査して探すため、食い違っていても動きます。
- **修正内容（汎用）**: 検索結果として「見つかった場所（キー）」を返し、それを使って更新・削除する。実際の置き場所を正とする。
- **予防**: 冗長なデータ（キーと値の二重持ち）があるときは、食い違いが起きても壊れない実装にする。既存の実装（アプリ側）の探し方に合わせる。
- **この PR での例**: `operations/journal/journalStore.ts` の `findEntry`（`7c0b564`）。

### 2-4. 作成と更新で、検証のルールが非対称

- **重大度**: 低〜中
- **どういうときに起きるか**: 作成では「タイトルと本文の両方が空」を拒否するのに、更新では、両方を空にする更新が通るとき。
- **何が起きるか**: 作成では作れない状態（中身が空のエントリ）が、更新を経由すれば作れてしまいます。
- **原因**: 検証を「入力の形」の検証として書き、**「結果としてできあがる状態」の不変条件**として書いていませんでした。更新は「一部のフィールドだけ」を受け取るため、入力だけを見ると、両方空かどうかは分かりません。**更新後の値**を見る必要があります。
- **修正内容（汎用）**: 不変条件は、「更新を適用した後の値」に対して検証する。作成と更新で同じ検証関数を共有する。
- **予防**: 「作れない状態」を列挙し、他の操作（更新・インポート・同期）で作れてしまわないかを確認する。
- **この PR での例**: `journalInput.ts` の `assertEntryNotBlank`（作成・更新で共有、`7c0b564`）。

### 2-5. 書き込み頻度の違いを考えずに、既存の履歴の仕組みを流用する

- **重大度**: 中
- **どういうときに起きるか**: 人間が操作する頻度（手動で数回）を前提にした「履歴（スナップショット）を最大 N 件保持する」仕組みを、AI エージェント（短時間に何度も書く）が使うとき。
- **何が起きるか**: エージェントが N 回書くと、保持している履歴がすべてエージェントの書き込み由来になり、**人間が作った復元ポイントが全部押し出されて消えます**。
- **原因**: アプリの「アップロードのたびにスナップショットを 1 件作り、最大 5 件を保持する」という仕様を、そのまま API に当てはめました。この仕様は、**書き込みが人間の操作頻度であること**を暗黙に前提としています。書き手の性質（頻度・自動化）が変わると、同じ保持数の意味が変わります。
- **修正内容（汎用）**: 書き手ごとに保持の方針を変える。最新の履歴が同じ書き手（API）由来なら、新規作成せず**上書き**する。履歴の不変条件（「最新の履歴 ＝ 現在の状態」）は、上書きでも保つ。
- **予防**: 既存の仕組みを新しい書き手に流用するとき、「頻度」「量」「並行性」の前提が同じかを確認する。
- **この PR での例**: `snapshotWriter.ts`（`95130be`）。

### 2-6. 必要以上のデータを読む

- **重大度**: 低（コストと遅延）
- **どういうときに起きるか**: 書き込みのたびに、既存の履歴（最大 5 件 × 最大 1 MiB）を**本文ごと**読むとき。
- **何が起きるか**: 実際に使うのは「作成元の種別」と「ドキュメントの参照」だけなのに、毎回、最大約 5 MiB を読み、課金・遅延・トランザクションのロック時間が増えます。
- **原因**: アプリ側の取得処理（本文が必要な画面用）の形をそのまま真似ました。**用途に必要な項目だけを取得する**という視点が抜けていました。
- **修正内容（汎用）**: 必要なフィールドだけを取得する（Firestore の `select`）。取得しなかったフィールドを後で読んでいないか確認し、フェイクでも同じ制限を再現してテストする。
- **予防**: 大きなドキュメントを読む処理では、「使うフィールドはどれか」を毎回確認する。
- **この PR での例**: `syncWriter.ts` の `.select("deviceId")`（`18057c8`）。

## 3. トランザクションと原子性

### 3-1. 2 段階の操作の途中で失敗し、中途半端な状態が残る

- **重大度**: 中
- **どういうときに起きるか**: 「新しいものを保存する」→「古いものを削除する」を別々の呼び出しで行い、**2 つ目だけが失敗する**とき（通信断、権限エラーなど）。API キーの再発行や、複数キーの失効が該当します。
- **何が起きるか**:
  - 再発行: 新しいキーは保存済みなのに、削除の失敗で例外になるため、画面は「発行に失敗」と表示し、**平文のキーは表示されません**。利用者は誰も知らないキーがサーバーに残り、古いキーは有効なままです。「古いキーは無効になったのか」も分かりません。
  - 失効: 複数のキーを `Promise.all` で 1 件ずつ消すと、一部だけ消えた状態になります。
- **原因**: 1 つの意図（「キーを入れ替える」）を、**独立した複数の書き込み**として実装しました。エラー表示は「操作全体が失敗した」ことを表しますが、実際の状態は「一部だけ成功」で、**表示と実際の状態が食い違いました**。また、「失敗を握りつぶして成功とみなす」案は、古いキーが有効なまま残ることを利用者から隠すため、安全面で不適切でした。
- **修正内容（汎用）**: 1 つの意図に対応する書き込みは、**バッチ（またはトランザクション）にまとめて原子的にする**。成功すれば全部反映、失敗すれば何も変わらない。これで「エラー表示 ＝ 実際の状態」が一致する。
- **予防**: 「A してから B する」処理を見つけたら、「B だけ失敗したらどうなるか」を必ず考える。エラー表示と実際の状態が一致するかを確認する。
- **この PR での例**: `apiKeyRepository.ts` の `replaceApiKeyHash`・`deleteApiKeyHashes`（`4231a40`）。

### 3-2. バッチとルールの相性（存在しないドキュメントの削除）

- **重大度**: 低（理解しておくべき性質）
- **どういうときに起きるか**: バッチで複数のドキュメントを削除するとき、**一覧取得からコミットまでの間に、別のタブや端末で一部がすでに消された**場合。
- **何が起きるか**: ルールの `delete` 条件が `resource.data.uid == request.auth.uid` のとき、存在しないドキュメントでは `resource` が null になり、条件が評価エラー（拒否）になります。バッチは原子的なので、**全体が失敗して何も変わりません**。
- **原因**: ルールは、書き込み 1 件ずつ評価されます。存在しないドキュメントの削除は、通常の Firestore では成功しますが、**ルールが既存ドキュメントのフィールドを参照していると拒否されます**。バッチ化で「1 件失敗すると全体が失敗する」性質が加わりました。
- **扱い方（汎用）**: 失敗しても何も変わらず、一覧を取り直して再試行すれば成功するため、実害は小さい。**この前提を、コード（JSDoc）に明記する**。
- **予防**: バッチ化したときは、ルールの評価（書き込みごと）と、競合時の挙動を確認し、前提を文書化する。
- **この PR での例**: `apiKeyRepository.ts` の JSDoc（`60cf6dc`）。

### 3-3. 並行実行の競合は、「実際に起きる条件」で採否を判断する

- **重大度**: 判断の事例
- **どういうときに起きるか**: 複数のタブから、同時に「再発行」を押したとき。
- **指摘の内容**: 旧キーの一覧取得がバッチの外にあるため、両方が同じ旧一覧を読み、新しいキーが 2 本残るのではないか、という指摘でした。
- **検討の結果（見送り）**:
  1. 旧キーがある状態では、先にコミットした側が旧キーを削除します。後からコミットする側のバッチは、**すでに消えた旧キーの削除がルールで拒否される**ため全体が失敗し、新しいキーは 2 本残りません。
  2. 残るのは、「キー未発行の状態で、複数のタブから数ミリ秒差で同時に初回発行した」場合だけです。この場合も、2 本とも同じ本人の uid に紐づき、それぞれ本人に表示されたキーなので、漏えいではありません。次の再発行や失効で、まとめて消えます。
  3. 提案の対策（uid ごとの固定ドキュメントをトランザクションで更新）は、Web SDK のトランザクションではクエリが使えないこと、ルールの再設計と別途のデプロイが必要になることから、**影響に対して過剰**でした。
- **教訓（汎用）**: 競合の指摘には、**① 実際に起きる条件、② 起きたときの影響、③ 対策のコスト**を並べて判断する。「理論上起こりうる」ことと「対応すべき」ことは別。見送る場合は、理由を記録する（スレッドの返信など）。

### 3-4. トランザクション内の読み取りは、書き込みより先に済ませる

- **重大度**: 設計上の必須事項
- **どういうときに起きるか**: Firestore のトランザクション内で、書き込みを行った後に、読み取りを行うとき。
- **何が起きるか**: 実際の SDK では、「すべての読み取りは、すべての書き込みより先」というエラーになります。
- **原因と対策**: この制約は、テストで使うフェイクが再現していなければ、テストをすり抜けます（6-1 を参照）。実装では、先にユーザードキュメントと履歴を読み、その後に判定・書き込みの順にしました。トランザクションの本体（コールバック）は、リトライされることがあるので、**純粋（副作用なし）**に保つ。
- **この PR での例**: `syncWriter.ts`。

## 4. セキュリティルール

### 4-1. 設定ファイルの編集箇所を誤り、別のブロックに入れてしまう

- **重大度**: 高（デプロイの失敗、または既存機能の停止）
- **どういうときに起きるか**: 似た構造のブロックが複数ある設定ファイル（Firestore ルールなど）に、**テキストの位置を基準にした自動編集**で行を追加するとき。
- **何が起きるか**: ルールの検証用の行（`keyHash.matches(...)`）が、`apiKeys` ではなく、別のコレクション（`bugReports`）の `create` 条件に入りました。そのブロックには `keyHash` という変数が存在しないため、デプロイ時にルールのコンパイルが失敗するか、通ったとしても**すべての不具合報告の作成が拒否**されるところでした。
- **原因（詳細）**:
  1. 指示は「`allow create` の `request.auth != null` の次の行に追加する」でした。この文言は、**ファイル内の複数のブロックに当てはまります**。自動編集を行った担当は、最初に見つかった位置（`bugReports`）に挿入しました。
  2. 担当の報告は「括弧の数は釣り合っている（20 対 20）」というものでした。**括弧の数の確認は、行がどのブロックに入ったか（スコープ）を検出できません**。構文としては正しいのです。
  3. ルールには自動テスト（エミュレータ）が無く、実行して検証する手段がありませんでした。
  4. 最終的に、**差分を読むレビュー**で発見されました（`git diff` に、意図したブロック以外の変更が出ていたため）。
- **修正内容（汎用）**: 行を正しいブロックへ移す。
- **予防**:
  - 自動編集の指示は、位置ではなく**ブロックの名前で特定する**（「`match /apiKeys/{keyHash}` の `allow create` に」）。
  - 編集後は、**差分が意図した箇所だけか**を必ず確認する（`git diff` で変更が複数のブロックにまたがっていないか）。括弧の一致のような形式的な確認では代わりにならない。
  - 設定ファイルにも、可能ならテスト（ルールのエミュレータなど）を用意する。無い場合は、デプロイ後の手動確認の手順を残す。
- **この PR での例**: `firestore.rules`（`845b2a8`）。

### 4-2. 認証・秘密情報の扱いの確認項目（問題が無かった点を含む）

レビューで確認し、問題が無かった点です。新しい API を作るときの確認項目として残します。

- 認証を、ルーティングより**前**に行う（キーが無ければ、エンドポイントの存在も分からない）。
- 形式が不正なキーは、データベースを引かずに拒否する（無駄な読み取りと、列挙攻撃の足がかりを避ける）。
- 秘密情報は、ハッシュだけを保存し、平文は保存・ログ出力しない。クライアントとサーバーで、ハッシュの計算方法（エンコード・大文字小文字）を揃え、テストで固定する。
- 想定外のエラーは、詳細を返さず、ログにだけ残す。
- ルールの作成条件で、ID の形式・所有者・サーバー時刻（`createdAt == request.time`）・許可するフィールド（`keys().hasOnly`）を検査し、更新を禁止する（他人のキーの上書きを防ぐ）。
- リクエスト本文の未知キーは拒否する（`__proto__` などの特殊なキーによる汚染の防止にもなる）。

## 5. UI・状態管理・アクセシビリティ

### 5-1. 1 つの結果を、複数の状態で表現して矛盾する

- **重大度**: 中
- **どういうときに起きるか**: 「コピーに成功した」という結果を表す `copied`（真偽値）と、失敗を表す `error`（文字列）を**別々の状態**として持ち、それぞれが、もう一方を更新しないとき。
- **何が起きるか**: 2 通りの矛盾が起きました。
  - 成功の後に再試行が失敗 → 「コピーしました」と「コピーに失敗しました」が**同時に**表示される。
  - 失敗の後に再試行が成功 → 同じく両方が表示される。
- **原因（詳細）**:
  1. 「コピーの結果」は、本来は「未実施 / 成功 / 失敗」のどれか 1 つです。これを、**独立した 2 つの変数**で表現したため、「成功かつ失敗」という存在してはならない組み合わせが作れてしまいました。
  2. 最初の修正では、「失敗したときに `copied` を戻す」だけを実装しました。**逆方向（成功したときにエラーを消す）が漏れていました**。状態遷移は、「A→B」と「B→A」の両方を設計する必要があります。
  3. エラーは、複数の操作（取得・発行・失効・コピー）が共有する**1 つの文字列**です。成功時に無条件で消すと、**他の操作のエラー（例: 再発行の失敗）まで消えて**しまいます。
- **修正内容（汎用）**:
  - 失敗時に、成功の表示を解除する。
  - 成功時に、**自分の操作のエラーだけ**を消す。エラーが共有されている場合は、関数形式の更新（`setError(prev => prev === 自分のエラー ? null : prev)`）で、該当するものだけを消す。
  - 各遷移（成功→失敗、失敗→成功）を、別々のテストで確認する。他の操作のエラーが残ることもテストする。
- **予防**: 1 つの概念に複数の状態を使うなら、「存在してはならない組み合わせ」が作れないかを確認する。可能なら、1 つの状態（列挙型）にまとめる。
- **この PR での例**: `useCopyApiKey.ts`、`useApiKeyState.ts`（`1d6ce18`、`9ab2617`）。

### 5-2. 初期取得に失敗すると、操作できなくなる

- **重大度**: 低
- **どういうときに起きるか**: 画面を開いたときの状態取得が、一時的な通信障害で失敗したとき。
- **何が起きるか**: 状態が「確認中」のまま変わらず、操作ボタンが無効のままになります。エラー文言は出ますが、**復帰の方法が分かりません**（実際は、ページの再読み込みで直ります）。
- **原因**: 取得は、画面の表示時に 1 回だけ行う作りで、失敗時の再取得の手段がありませんでした。ボタンを「状態が確定するまで無効」にしたことと組み合わさり、復帰できなくなりました。
- **修正内容（汎用）**: 最小限の対応として、エラー文言に、復帰の方法（「ページを再読み込みしてください」）を書く。再試行ボタンを追加するかどうかは、障害の頻度・影響・変更の大きさで判断する（今回は一時的な障害のみのため、過剰と判断）。
- **予防**: 「失敗したらどう復帰するか」を、各非同期処理で確認し、利用者に伝わる文言にする。
- **この PR での例**: `locales/ja.json`（`1d6ce18`）。

### 5-3. 動的に変わる表示が、スクリーンリーダーに通知されない

- **重大度**: 中（アクセシビリティ）
- **どういうときに起きるか**: ボタンを押したり、自動で取得が完了したりして、**フォーカスが動かないまま**画面の一部（状態、コピー結果、エラー）が変わるとき。スクリーンリーダー利用者には、変化が伝わりません。
- **原因**:
  1. 通常のテキストの変更は、スクリーンリーダーに通知されません。通知されるのは、**ライブリージョン**（`role="status"`、`role="alert"`、`aria-live`）として公開された領域の変化だけです。
  2. さらに、**条件付きで要素ごと差し込む**と、読み上げられないスクリーンリーダーがあります。ライブリージョンは、「最初から存在する領域の中身が変わる」ときに通知されるためです。
- **修正内容（汎用）**:
  - 状態の変化・操作の結果は、`role="status"`（`aria-live="polite"`）の領域で公開する。
  - エラーは `role="alert"` にする。
  - 領域は**常に描画し、中身だけを切り替える**。再描画で領域が作り直されないことを、テストで確認する（同じ DOM ノードのまま、文言だけが変わること）。
  - 状態表示は、ラベルと値を含む外側の要素に付ける（値だけだと「未発行」とだけ読まれ、文脈が欠ける）。
- **予防**: 動的に変わる表示を追加するときは、「フォーカスが動かない更新か」を確認し、ライブリージョンにする。同じ画面に複数の領域があっても、変わるきっかけが別々なら、同時に読み上げが重なることはない。
- **この PR での例**: `IssuedApiKeyPanel.tsx`、`ApiKeyPanel.tsx`（`1d6ce18`）、`ApiKeyStatusRow.tsx`（`6834a3b`）。

### 5-4. effect がコールバックの参照に依存し、不要に再実行される

- **重大度**: 低（呼び出し側の書き方次第で顕在化）
- **どういうときに起きるか**: 「初回に 1 回だけ取得する」フックが、コールバック（失敗時の通知）を、effect の依存配列に入れているとき。呼び出し側がレンダリングごとに新しい関数を渡すと、**そのたびに再取得**します。
- **何が起きるか**: 取得が重複し、状態の更新が遅れて到着して、テストでは「`act` の外での更新」の警告が出ました。
- **原因**: 依存配列に入れた関数の参照は、レンダリングごとに変わりうる値です。フックが、**呼び出し側が参照を安定させること**に暗黙に依存していました。
- **修正内容（汎用）**: コールバックは `ref` に保持して、effect の依存配列から外す（最新の関数を呼びつつ、再実行はしない）。「参照が変わっても再取得しない」ことと、「取得中に差し替えられたら最新の関数を呼ぶ」ことを、テストで固定する。
- **予防**: 「1 回だけ実行したい処理」の依存配列に、関数や配列を入れていないか確認する。
- **この PR での例**: `useApiKeyPresence.ts`（`509dd38`）。

### 5-5. 実行環境（Firebase 未設定）を考慮しない表示

- **重大度**: 低
- **どういうときに起きるか**: Firebase を設定していないローカルモードで、Firebase に依存する機能（キーの保存先が Firestore）の画面を表示したとき。
- **何が起きるか**: 常に「状態を取得できませんでした」というエラーが表示され、ボタンも無効のままになります。
- **原因**: 機能が依存する外部サービスが、**使えない構成がある**ことを、画面側が考えていませんでした。
- **修正内容（汎用）**: その構成では、機能の画面を**表示しない**（機能自身が、依存する条件を判断する）。表示する／しないの判断は、機能の入口のコンポーネントで行う。
- **この PR での例**: `ApiKeySection.tsx`（`509dd38`）。

## 6. テスト

### 6-1. フェイクが本物より甘く、テストが空振りする

- **重大度**: 中
- **どういうときに起きるか**: 外部サービス（Firestore）の代わりに、**テスト用のフェイク**を使っているとき。
- **何が起きるか**: 本物では失敗する実装が、フェイクでは成功し、**テストは緑のまま不具合を見逃します**。
- **原因（詳細）**: 最初のフェイクは、次の点で本物と違いました。
  - トランザクションの書き込みが**即時**に反映され、失敗時の巻き戻しがない（本物は、コミット時にまとめて反映し、失敗したら何も反映しない）。
  - 書き込みの後に読み取りをしても失敗しない（本物は失敗する）。
  - 存在しないドキュメントへの更新が成功する（本物は NOT_FOUND）。
  - フィールドの絞り込み（`select`）を再現しない。

  これらは、実装が「読み取りを先に済ませる」「存在を確認してから更新する」「必要な項目だけ読む」ことを**テストで保証できない**状態でした。フェイクは、「テストを通りやすくする」方向に簡略化されがちで、その簡略化が、検証したい性質を消してしまいます。

- **修正内容（汎用）**: フェイクを、本物の**主な制約**に近づける。さらに、**フェイク自身のテスト**を書き、再現しているはずの制約（書き込み後の読み取りでエラー、コミット時の一括反映、存在しない更新の失敗、投影）を固定する。
- **予防**: フェイクを作るときは、「本物のどの制約に、実装が依存しているか」を列挙して再現する。可能なら、エミュレータでの統合テストも用意する。
- **この PR での例**: `__tests__/fakeFirestore.ts` と `fakeFirestore.test.ts`（`18057c8`）。

### 6-2. モックの実装が、次のテストに漏れる

- **重大度**: 低
- **どういうときに起きるか**: あるテストで `mockRejectedValue(...)` を設定し、後続のテストが成功を期待するとき。
- **何が起きるか**: 後続のテストが、前のテストの失敗の設定を引き継いで落ちます。順序や並列度によって結果が変わる、不安定なテストになります。
- **原因**: `jest.clearAllMocks()` は、**呼び出しの記録だけ**を消し、`mockResolvedValue` などで設定した**実装は消さない**ためです。名前から、全部リセットされると誤解しやすい仕様です。
- **修正内容（汎用）**: 各テストの前（`beforeEach`）で、**必要な既定の実装を毎回設定し直す**（成功のケースを既定にする）。または、`resetAllMocks` を使う。
- **この PR での例**: `apiKeyService.test.ts`（`4231a40`）。

### 6-3. 実行環境の差（テスト環境にあるもの・ないもの）

- **重大度**: 低
- **どういうときに起きるか**: ブラウザ向けのコード（`crypto.subtle`、`TextEncoder`）を、jsdom 環境のテストで動かすとき。
- **何が起きるか**: 「`TextEncoder is not defined`」のように、本番のブラウザでは存在する API がテスト環境に無く、テストが失敗します。
- **原因**: jsdom は、ブラウザの一部の API しか実装していません。
- **修正内容（汎用）**: テストの側で、Node の実装を差し込む（`webcrypto`、`util.TextEncoder`）。**本番コードには、テストのための分岐や import を入れない**。差し込みが、本番コードに漏れていないことを確認する。lint で `require()` が禁止されている場合は、`jest.requireActual` を使う。
- **この PR での例**: `apiKeyGenerator.test.ts`（`ed6e435`）、`SettingsPage.test.utils.ts`。

### 6-4. テスト名と中身が合わない・成功したことを確認していない

- **重大度**: 低
- **どういうときに起きるか**:
  - テスト名が「UTF-8 のハッシュにして保存する」なのに、実際は「関数が呼ばれたこと」だけを確認している。

- **何が起きるか**: 将来の変更でテストの前提が崩れても（例: 失効失敗でキーの表示が消え、コピー処理が何もしなくなる）、テストが緑のまま通り、**意図した状況を検証できなくなります**。
- **原因**: 「期待する結果」だけを書き、「その結果に至る前提が成り立っていること」を書いていませんでした。
- **修正内容（汎用）**: 前提（表示中のキーが残っている、コピーが実行された、`copied` が真）も、アサーションで明示する。テスト名は、実際に確認していることに合わせる。
- **予防**: 「このテストは、前提が崩れたら落ちるか」を自問する。
- **この PR での例**: `useApiKeyState.flows.test.ts`（`6834a3b`）、`apiKeyService.test.ts`。

### 6-5. 境界値のテストが、既存の不具合を見つける

- 1-3 の日付の不具合は、リファクタリングの際に境界値のテストを追加して、はじめて見つかりました。**最初のテストが、典型的な値だけで構成されていた**ためです。

## 7. 構造（単一責任）

構造に関する指摘は、動作の誤りではなく、**将来の変更で壊れやすい・理解しづらい**という問題でした。目安は、**「1 つのファイルが変わる理由が 1 つだけ」**であることです。行数は、このプロジェクトのガイド（理想 80 行以内、許容 120 行程度）に従いました。

### 7-1. 1 つのファイルに複数の責務が同居している

- **どういうときに起きるか**: 最初に「動かす」ことを優先し、関連する処理を 1 つのファイルに置き続けたとき。
- **この PR での例と、分け方の考え方**:

| 元のファイル                             | 混在していた責務                                                              | 分割の軸                                                       |
| ---------------------------------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 検証ヘルパー（172 行）                   | 本文の検査、文字列・金額・日付・列挙の各検証、クエリ検証、日付判定            | 検証の**種類**ごと                                             |
| 支出・ジャーナルの操作（約 170・140 行） | データの読み書き、入力の検証、エンティティの生成・更新、4 つの操作            | 「データ（ストア）」「入力」「エンティティ」「操作」の**層**   |
| 同期の書き込み（107 行）                 | `lastModified` の計算、スナップショットの組み立てと保存、トランザクション制御 | 変更の**理由**（時刻の規則、履歴の保持方針、トランザクション） |

- **分け方の指針**: 「ファイルを変更する理由を列挙し、2 つ以上あれば分ける」。純粋な計算と、外部との入出力は分ける。小さく分けても、**公開する窓口（`index.ts`）は変えず**、既存のテストを維持する。分割の前後で、既存のテストがそのまま通ることを、挙動が変わっていない根拠にする。

### 7-2. 同じ責務が複数の場所に重複している

- **どういうときに起きるか**: 同じ形のコードが、3 つの操作モジュールにコピーされたとき。
- **この PR での例**:
  - 「更新するフィールドが無い」エラーの生成が、3 か所に重複 → 1 つの関数にまとめた。

### 7-3. 依存の向きが逆になっている

### 7-4. 使われていないコードと、不要な再公開

- **何が起きるか**: 公開面が広がり、「使ってよいもの」が分かりにくくなります。デッドコードは、将来の誤解を生みます。
- **修正内容（汎用）**: 本番コードから使われていない公開を削除する。テストは、本来のモジュールから直接インポートする。`index.ts` は、実際に外部が使うものだけを公開する。
- **予防**: リファクタリングの後に、「どこからも使われていない export」を機械的に探す（検索で、定義ファイル以外の参照数を数える）。

### 7-5. 機能の境界（UI の置き場所と公開窓口）

- **どういうときに起きるか**: ある機能（API キー）の UI を、別の機能（設定）のフォルダに置いたとき。

## 9. ビルド・環境・運用

### 9-1. 既存のエラーが、デプロイの前処理（predeploy）を止める

- **重大度**: 高（機能を出せない）
- **どういうときに起きるか**: デプロイの設定（`firebase.json`）が、デプロイ前に `tsc`（ビルド）を実行し、**テストファイルも含めて**型検査するとき。既存のテストに型エラーが 1 つでもあると、ビルドが失敗の終了コードになります。
- **何が起きるか**: 自分の変更とは無関係でも、**デプロイが止まります**。実装中のテストでは気づかず、ビルドを、デプロイと同じ手順で実行して初めて見つかりました。
- **原因**: 型検査の対象に、本番に不要なテストが含まれていたこと。既存の型エラー（`token` プロパティへのアクセス）が、長い間放置されていたこと。デプロイ前の手順（ビルド）を、開発中に実行していなかったこと。
- **修正内容（汎用）**: 既存のテストの型エラーを最小限に直す（今回は 1 行）。範囲外の変更になる場合は、理由を PR に明記する。
- **予防**: 開発中から、デプロイ前の手順（ビルド・lint）を、デプロイと同じコマンドで実行する。「自分の変更が原因ではないエラー」も、デプロイを止めるなら対応対象として扱う。
- **この PR での例**: `a8ba5a6`。

### 9-2. 管理外のディレクトリが、リポジトリ全体の lint・テストを壊す

- **重大度**: 低〜中（環境の問題）
- **どういうときに起きるか**: 過去に作った作業用のディレクトリ（`.worktrees/`）が、`.gitignore` で Git の管理外にはなっているが、**ESLint と Jest の対象からは外れていない**とき。
- **何が起きるか**: 全体の lint（`npm run lint`）が、そのディレクトリの 200 件超のエラーで失敗し、`npm run verify` が通りません。テストを全件実行すると、そのディレクトリ内のコピーのテストまで実行され、失敗します。
- **原因**: Git の管理外であることと、ツールの対象外であることは、**別の設定**です。ESLint・Jest の除外設定に、そのディレクトリが入っていませんでした。CI では、そのディレクトリが存在しないため問題になりません。
- **扱い方（汎用）**: この PR の範囲外の既存の問題として、**同じ内容の検証を、対象を絞って実行する**（`.worktrees` を除外した eslint・jest）。結果を報告するときは、どこが通らず、なぜ範囲外かを正直に書く。恒久対応として、ESLint・Jest の除外設定に追加する。
- **予防**: 「検証コマンドが通らない」ときに、自分の変更が原因かを切り分ける（エラーの出ているパスで判定する）。

### 9-3. デプロイの順序

- **どういうときに起きるか**: ルールと関数と画面（アプリ）を、別々にデプロイするとき。
- **何が起きるか**: ルールのデプロイ前に画面が公開されると、キーの発行がエラーになります（安全側に失敗する）。
- **指針**: **ルール → 関数 → アプリ**の順にデプロイする。ルールには自動テストが無いため、デプロイ後にプレイグラウンドで、本人・他人・更新・未認証のケースを手動で確認する手順を、PR に残す。

### 9-4. 古いビルド成果物が、分割後のモジュールを隠す（デプロイした関数が壊れる）

- **重大度**: 高（本番で、有効な認証のリクエストがすべて 500 になった）
- **どういうときに起きるか**: ファイルをディレクトリに分割（`validation.ts` → `validation/`）したあと、**`lib/` を消さずに** `tsc` でビルドして、そのままデプロイしたとき。
- **何が起きるか**: デプロイした関数が、`TypeError: assertKnownQueryKeys is not a function` で落ち、認証に成功したすべてのリクエストが 500 になります。**キーが無い・不正なリクエストは 401 のまま正常に見える**ため、認証失敗だけのスモークテストでは見つかりません。
- **原因（詳細）**:
  1. `tsc` は、ソースから出力を作るだけで、**ソースが消えた出力は削除しません**。そのため、`validation.ts` を `validation/index.ts` に分けても、古い `lib/agentApi/validation.js` が残ります。
  2. Node の `require("./validation")` は、**同名のファイル（`validation.js`）を、ディレクトリ（`validation/index.js`）より先に解決します**。結果として、リファクタリング前の古い実装が読み込まれ、新しく足した関数（`assertKnownQueryKeys`）が存在しません。`expenses.ts`・`journal.ts` も同じ状態で、古い実装が読み込まれる状態でした。
  3. ローカルのテスト（ts-jest）は、TypeScript の**ソースを直接読む**ため、`validation.ts` が無ければディレクトリを読みます。**ビルド成果物を使っていない**ので、この不具合を検出できません。CI は、毎回まっさらな環境でビルドするため、古い出力が存在せず、同じく再現しません。つまり、**ローカルに古い出力が残った開発者のマシンからデプロイしたときだけ**起きる、環境依存の不具合です。
  4. デプロイ前に、`predeploy` で `tsc` が走り、成功しました。**成功＝正しい出力が作られた、ではなく、古い出力も残っている**ことを、誰も確認していませんでした。
- **修正内容（汎用）**: ビルドの前に、出力ディレクトリを削除する（`build` を `clean && tsc` にする）。デプロイ前の処理（`predeploy`）が `build` を呼ぶため、デプロイでも必ず clean ビルドになる。この構成を、テストで固定する。
- **予防**:
  - ファイルとディレクトリの分割・改名をしたら、**ビルド出力を一度削除してから**ビルド・デプロイする。
  - 出力ディレクトリを持つビルドは、常に clean ビルドにする。
  - デプロイ後のスモークテストは、**認証に成功するリクエスト**（有効なキー）で行い、関数のログも確認する（認証失敗だけでは、認証より後ろのコードを通らない）。
- **この PR での例**: `firebase-functions/package.json` の `clean`・`build`、`tools/__tests__/functionsBuildScript.test.ts`。

### 9-5. 認証情報の種類によって、SDK が使えない機能がある

- **重大度**: 低（ツール作成時の落とし穴）
- **どういうときに起きるか**: `firebase login` が保存している認証情報（リフレッシュトークン形式、`authorized_user`）を、Admin SDK に渡して、Firestore を操作しようとしたとき。
- **何が起きるか**: Auth は動くのに、`admin.firestore()` が「証明書の認証情報か、アプリケーションのデフォルト認証情報（ADC）が必要」というエラーになります。
- **原因**: Admin SDK の Firestore は、認証情報の種類を限定していて、リフレッシュトークン形式を受け付けません（Auth は受け付ける）。同じ SDK でも、機能ごとに受け付ける認証情報が違います。
- **修正内容（汎用）**: Firestore だけ、下位のライブラリ（`@google-cloud/firestore`）に、認証クライアント（`GoogleAuth`）を直接渡して使う。Auth は Admin SDK のままにする。**実際に本番に接続して確認する**まで、使えるかどうかは分からないため、読み取りだけのコマンドで先に動作確認する。
- **この PR での例**: `tools/api-key/initAdmin.mjs` の `initWithFirebaseCliLogin`。

## 10. 作業手順とレビュー運用の落とし穴

### 10-1. 自動編集・サブエージェントの報告を、そのまま信じない

- **起きたこと**: 4-1 のルールの誤り。担当の報告は「括弧の数は 20 対 20 で OK」でした。また、報告書の行数・テスト数が、実際と食い違うこともありました。
- **原因**: 報告は、**担当が確認した範囲の自己申告**です。確認の方法が、検証したい性質（スコープ）に合っていないことがあります。
- **指針**: 報告を受けたら、**実際のコマンドの出力・差分で、独立に再検証する**（型検査、テスト、lint、`git diff` の範囲）。「検証した」という文面ではなく、「何を、どのコマンドで確認したか」を見る。

### 10-2. 自動置換は、位置の曖昧さと、整形の副作用に注意する

- **起きたこと**:
  - 文字列の置換が、整形ツール（Prettier）による改行・折り返しの変更で**空振りした**。置換が失敗したことに気づかないと、修正が適用されないまま進む。
  - 整形ツールを、ディレクトリ全体に実行して、無関係なファイルに差分が出た。
  - 本文から行を削除する指示が、複数の場所に当てはまった（4-1）。
- **指針**:
  - 置換は、**一致しなかったら失敗する**書き方にする（`assert old in s`）。
  - 整形は、**自分が触ったファイルだけ**に実行し、全体への実行は避ける。やむを得ず広げた場合は、整形だけの差分であることを確認し、報告する。
  - 編集後は、差分の範囲を確認する。

### 10-3. シェル・OS の違い（macOS + zsh）

- `sed -i` は、macOS（BSD 版）では、書式が異なり、GNU 版の書き方では動かない → ファイルの編集は、専用のツールか Python で行う。
- zsh では、一致するファイルが無いとき、グロブ（`--include=*.ts` など）がエラーになる → クォートする。
- `cd` で移動した位置が、次のコマンドにも持ち越される → 絶対パスを使う。
- **zsh では、変数名 `path` が環境変数 `PATH` と連動している**。`for path in ...` のようにループ変数に使うと、`PATH` が上書きされ、それ以降 `curl`・`python3`・`seq` などが「command not found」になる → `endpoint` など、別の名前にする（`PATH` と連動する名前: `path`、`cdpath`、`fpath`、`manpath`、`module_path`）。
- 長い待機は、フォアグラウンドの `sleep` ではなく、バックグラウンドで実行して通知を待つ。

### 10-4. 自分の PR は Approve できない

- GitHub の仕様で、PR の作成者本人は、自分の PR を Approve できない（422）。
- **扱い方**: まず Approve を試し、拒否されたら、`COMMENT` で投稿し、**判定を本文に明記する**（「Approve 相当」）。インラインの指摘は、同じレビューにまとめて投稿する。

### 10-5. レビューツールの誤検知

- **起きたこと**: Copilot が、計画書の文中に `******` があると指摘した。実際のファイルには存在せず、`Bearer キー…` という文字列が、レビュー画面でシークレットとしてマスク表示されたものだった。
- **指針**: 指摘は、**実際のファイルと差分で事実を確認**する。誤検知なら、理由を返信して Resolve する（黙って無視しない）。

### 10-6. レビューの依頼は、取り消しても結果が届くことがある

- レビューを依頼してから取り消しても、**取り消し前に開始した分の結果は届く**。届いた指摘は、内容を確認して、対応済みのものは「対応済み」と返信して Resolve する。

### 10-7. 指摘のトリアージの基準

指摘ごとに、次の基準で「対応する／見送る」を決めました。どちらの場合も、理由を返信に残します。

| 観点         | 対応する方向                                                     | 見送る方向                                                      |
| ------------ | ---------------------------------------------------------------- | --------------------------------------------------------------- |
| 実害         | データ消失・誤表示・利用者の混乱                                 | 起きる条件が極めて限られ、影響も小さい                          |
| 方針との整合 | プロジェクトの方針（欠損の保護、公開は `index.ts` 経由）に反する | 受け入れ済みの設計判断（最終書き込み優先、匿名 uid への紐付け） |
| 変更の大きさ | 数行・属性の追加・文言の修正                                     | ルールの再設計や、別デプロイが必要                              |
| 過剰さ       | 現実の障害を防ぐ                                                 | 想定しにくい障害のための仕組み                                  |

- **ループの運用**: 「サブエージェントによるレビュー → 別のサブエージェントによるトリアージ → 修正（テストの拡充、コミット、プッシュ、PR 本文の更新、スレッドの Resolve）」を、**対応すべき指摘が無くなるまで**繰り返す。各ラウンドの重要な変更点を、レビュアーに「重点的に確認してほしい点」として渡す。

## 13. 管理者向け CLI・秘密を扱うツール

PR #176（API キーを CLI から発行する機能）では、ローカルでのサブエージェントによるレビューを 4 周回しました（1 周目: 多数、2 周目: 4 件、3 周目: 2 件、4 周目: 指摘なし）。続いて PR 上でのレビューを 1 回行い、指摘はありませんでした。この章は、その指摘を、**「秘密（キー・トークン）を扱う」「管理者権限で動く」「ローカルのファイルを書き換える」ツール**に共通の形にまとめたものです。

このようなツールは、Web の API と違って、**入力を送る人も実行する人も、ほぼ同じ開発者**です。そのため、検証や表示が甘くなりがちですが、**実行する環境（OS・シェル・設定・権限・ファイルの状態）が人によって違う**ことと、**管理者権限で、取り消せない操作をする**ことが、問題の原因になります。

### 13-1. 取り消せない操作のあとに、失敗する処理を置いている（秘密が失われる）

- **重大度**: 高（発行したキーが失われ、使えないキーだけが残る）
- **どういうときに起きるか**: 「キーを発行して（保存して）から、ファイルに書き込む」順番の処理で、**書き込み先が書き込み不可**（ディレクトリの権限がない、読み取り専用のファイル、通常のファイルではない、など）のとき。
- **何が起きるか**: サーバー側にはキーのハッシュが保存済みですが、**平文のキーは画面にもファイルにも出ていません**。平文は再表示できない設計のため、利用者はキーを取り戻せず、使われないキーがアカウントに残ります。
- **原因（詳細）**:
  1. 「発行」は、**ハッシュを保存した時点で取り消せない**操作です。一方、「ファイルへの書き込み」は、環境に依存して**失敗しうる**操作です。取り消せない操作を先に、失敗しうる操作を後に置くと、後ろが失敗したときに、前の結果だけが残ります。
  2. 平文のキーは、**メモリ上にしか存在しません**。書き込みが失敗して例外を投げると、プロセスが終了し、平文は失われます。
  3. 「正常系では、書き込みに成功する」という前提で書いていて、**失敗したときに、秘密をどこへ出すか**を設計していませんでした。
- **修正内容（汎用）**:
  - **事前の確認**: 取り消せない操作の**前に**、失敗しうる条件（ディレクトリへの書き込み、ファイルの読み書き、通常のファイルか）を確認する。
  - **失敗したときの退避**: 確認をすり抜けて後から失敗した場合（確認と実行の間の競合など）に備えて、**秘密を標準エラーに出してから**、例外を伝える。標準出力ではなく標準エラーにするのは、標準出力をパイプやログに流している場合に、秘密が混ざらないようにするため。
  - 「書き込みました」という成功の表示は、**書き込みに成功してから**出す。
- **予防**: 「この処理が途中で失敗したら、秘密や結果はどこに残るか」を、順番ごとに考える。確認と実行の両方に、**同じ関数で書き込み先を決める**（13-3）。
- **この PR での例**: `tools/api-key/commands.js` の `runIssue`、`tools/api-key/envFileWriter.js` の `assertEnvFileWritable`、`formatters.js` の `formatEnvWriteFailure`。

### 13-2. 秘密のファイルを、権限と途中失敗に注意せずに書き込む

- **重大度**: 中〜高（他のユーザーに秘密が読まれる、ファイルが壊れる）
- **どういうときに起きるか**: 秘密を含むファイル（`.env.local` など）を、`writeFileSync` で直接書き、そのあとに `chmod 600` で権限を絞るとき。または、一時ファイルの名前を、プロセス ID だけで決めているとき。
- **何が起きるか**:
  - 作成から `chmod` までの**短い間**、ファイルが既定の権限（多くは 644）で存在し、同じマシンの他のユーザーがキーを読める。
  - 書き込みの途中でディスクがいっぱいになる・プロセスが中断すると、**元のファイルが空や途中までの状態で壊れる**。
  - 前回の実行がクラッシュして、同じプロセス ID の一時ファイル（平文のキー入り）が残っていると、次の実行がその名前の衝突で失敗する。しかも、失敗時の片付けが、**自分が作っていない他者のファイルを消してしまう**。
- **原因（詳細）**:
  1. 「作る」と「権限を絞る」が**別の操作**なので、その間に隙間が生まれます。権限は、**作成と同時に**指定するのが、唯一の安全な方法です（`open(…, { mode: 0o600, flag: "wx" })`）。
  2. 既存のファイルを直接上書きすると、書き込みの途中で失敗したとき、**元の内容が戻せません**。同じディレクトリの一時ファイルに書いて、`rename` で置き換えれば、置き換えは**原子的**（途中の状態が見えない）なので、元のファイルは、成功するか、元のままかのどちらかになります。
  3. プロセス ID は、**再利用される**・**クラッシュ後に同じ値になりうる**ため、一時ファイルの名前の一意性を保証しません。
  4. 失敗時の片付けで、「とにかく一時ファイルを消す」と書くと、**`wx`（既存なら失敗）が失敗した理由が「他者のファイルが既にある」**場合でも、そのファイルを消してしまいます。`wx` で作れなかった（`EEXIST`）なら、自分が作ったものではありません。
- **修正内容（汎用）**:
  - 一時ファイルを、**最初から権限 600**、`wx` で作り、`rename` で置き換える。
  - 一時ファイルの名前に、`randomBytes` の乱数を含める（`${path}.tmp-${pid}-${random}`）。
  - 片付け（`unlink`）は、**`EEXIST` 以外**のときだけにする。片付けの失敗は、元の例外を隠さないよう握りつぶす。
- **予防**: 秘密を書くコードでは、「作成時の権限」「途中失敗」「名前の衝突」「失敗時の片付けの対象」を、1 つずつ確認する。
- **この PR での例**: `tools/api-key/envFileWriter.js` の `writeEnvFile`、`tools/__tests__/envFileWriter.test.ts`（EEXIST では消さない、ランダムな名前）。

### 13-3. シンボリックリンクの扱いが、確認と実行でずれている

- **重大度**: 低〜中（意図した場所に書かれない、確認が効かない）
- **どういうときに起きるか**: 書き込み先（`.env.local`）が、**別の場所のファイルへのシンボリックリンク**（共有の秘密ファイルなど）のとき。
- **何が起きるか**:
  1. `rename` で置き換えると、**リンク自体が通常のファイルに置き換わり**、リンク先は更新されません。意図した場所に、新しいキーがありません。
  2. リンク先を更新するように直しても、事前の確認が、リンク**自体のディレクトリ**の権限しか見ていないと、リンク先のディレクトリにだけ書き込めない場合に、**確認を通ったあとで、発行後に失敗**します（13-1 の問題に戻る）。
  3. リンク先が存在しない**壊れたリンク**は、`existsSync` が `false` を返すため、「ファイルが無い」と同じに見え、リンクが通常のファイルで置き換えられます。
- **原因（詳細）**:
  1. `stat` / `exists` / `access` は、**リンクをたどる**一方で、`rename` は**リンクそのもの**を操作します。同じパスでも、操作によって「何を指すか」が違います。
  2. 確認と実行の**両方で、同じ「書き込み先の決め方」を使っていませんでした**。書き込み側だけを直すと、確認側とずれます。
  3. 「存在しない」には、「何も無い」と「壊れたリンクがある」の 2 通りがあり、`existsSync` では区別できません。
- **修正内容（汎用）**:
  - 書き込み先を決める処理（`resolveEnvTarget`）を **1 つの関数に切り出し**、確認と書き込みの**両方から使う**。存在するなら `realpathSync` でリンク先を求める。
  - 存在しないが `lstatSync` は成功する（壊れたリンク）場合は、**エラーにする**（黙って置き換えない）。
  - 確認は、リンク先のディレクトリの書き込み権限と、リンク先のファイルの読み書き権限で行う。
- **予防**: 「確認」と「実行」が、**同じ対象を同じ方法で決めているか**を確認する。ファイルを扱うコードは、リンクがあった場合を、テストに含める。
- **この PR での例**: `tools/api-key/envFileWriter.js` の `resolveEnvTarget`、`tools/__tests__/envFileWriter.test.ts`。

### 13-4. 設定ファイルの更新が、実在する書き方を想定していない

- **重大度**: 中（古いキーが残る・重複して追加される・他の行が注入される）
- **どういうときに起きるか**: `.env` 形式のファイルの `KEY=value` を、**正規表現などで更新する**とき。
- **何が起きるか**:
  - `export AGENT_API_KEY=old` の行を、別のキーと判断して、末尾に**同じキーを重複して追加**する。
  - `AGENT_API_KEY_OLD=1` のような、**前方が一致するだけの別のキー**を、誤って更新する。
  - 同じキーが複数行あると、先頭だけ更新して、**後ろの古い値が有効になる**（先頭と最後のどちらを使うかは、読み込むツールによって違う）。
  - 値に改行が含まれていると、**別のキーの行を注入**できる（`x\nB=injected`）。
  - `  KEY = value`（行頭や `=` の前後の空白）を認識できず、更新されない。
- **原因（詳細）**: 「`KEY=value` が 1 行ずつ並ぶファイル」という**理想の形だけ**を想定して、実際のファイルにある書き方（`export` の接頭辞、空白、重複、コメント）を洗い出さなかったためです。また、**値を信用して書き込む**（改行を検証しない）と、設定ファイルは「コードに近いもの」なので、注入の経路になります。
- **修正内容（汎用）**:
  - キーの判定は、`^(\s*(?:export\s+)?)(キー名)\s*=` のように、**行頭から、完全一致で**行う（前方一致の別のキーを除外）。
  - 同じキーが複数あるときは、**すべて更新する**。接頭辞（`export`）と行頭の空白は保つ。コメントアウトされた行（`# KEY=…`）は、更新しない。
  - 値に改行（`\n`・`\r`）が含まれていたら、エラーにする。**エラーメッセージには、キーの名前だけを含め、値は含めない**（13-6）。
- **予防**: 形式のある設定ファイルを書き換えるときは、「実在する書き方」をテストの入力として列挙する（空・末尾の改行なし・接頭辞・空白・重複・コメント・前方一致・特殊文字）。
- **この PR での例**: `tools/api-key/envFile.js` の `upsertEnvEntries`、`tools/__tests__/envFile.test.ts`。

### 13-5. 一覧・結果の表示が、取り違えと「一部だけ」の見落としを招く

- **重大度**: 中（別のアカウントにキーを紐づける、全件だと誤解する）
- **どういうときに起きるか**:
  - 管理者権限で、**対象を選んで取り消せない操作**（キーの発行・失効）をするとき。
  - **件数に上限がある一覧**（先頭 100 件）を、全件のように表示するとき。
- **何が起きるか**:
  - メールアドレスで対象を指定すると、そのメールが**未確認**のアカウント（本人がメールアドレスの持ち主であることを確認していないもの）に、気づかずに紐づけてしまう。
  - 匿名のアカウント（メールもログイン方法も無い）が「匿名」とだけ表示されると、**ログイン方法が無い理由**（匿名か、プロバイダーの情報が欠けているか）が分からない。
  - 101 件以上のアカウントがあるのに、先頭 100 件だけを表示し、「全部で 100 件」と読める。探しているアカウントが出てこなくても、存在しないと誤解する。
- **原因（詳細）**: 表示を、「データを列挙する」ものとして作り、**利用者がその表示を見て、何を判断するか**を考えていませんでした。特に、(1) 判断に必要な属性（メールの確認状態）を表示に含めていない、(2) **API のページングが「まだ続きがある」ことを `pageToken` で返していたのに、利用していなかった**、の 2 点です。
- **修正内容（汎用）**:
  - 取り違えると取り消せない操作の対象は、**判断に必要な属性をすべて表示**する（メールが未確認なら「（未確認）」と付ける）。
  - 一覧に上限があるときは、**ページングの続き（`pageToken`）の有無を、戻り値（`hasMore`）で返し**、「先頭 N 件のみ表示しています」と明示する。
  - 「属性が無い」状態には、**その理由が分かる名前**を付ける（「匿名（プロバイダーなし）」）。
  - 実装上の限界（競合、1 回のバッチの上限 500 件）は、**コード（JSDoc）と docs に書いておく**。
- **予防**: 一覧は、「全件か」「一部か」を、必ず利用者に分かるようにする。対象を指定する操作では、「別の対象を選んだら、気づけるか」を考える。
- **この PR での例**: `tools/api-key/userLookup.js`（`emailVerified`、`hasMore`）、`formatters.js`、`apiKeyStore.js` の JSDoc。

### 13-6. 例外のメッセージに、秘密が混ざる

- **重大度**: 中（トークンがログ・端末に出る）
- **どういうときに起きるか**: 秘密を含むファイル（認証情報の保存ファイル）を `JSON.parse` して、**パースに失敗した**とき。
- **何が起きるか**: `JSON.parse` の例外メッセージには、**入力の一部（失敗した位置の前後）が含まれる**ことがあります。それをそのまま表示・ログに出すと、リフレッシュトークンなどが画面や CI のログに出ます。
- **原因（詳細）**: 例外を「そのまま伝える」ことが、安全だと考えていました。ライブラリの例外メッセージの**中身は、呼び出し側が制御できません**。入力が秘密のとき、**入力を含みうる例外は、秘密を含みうる**ものとして扱う必要があります。
- **修正内容（汎用）**: 秘密を含む入力のパースでは、例外を捕まえ、**固定の文言**（「設定ファイルを JSON として読めません。`firebase login` をやり直してください」）に置き換える。元の例外は伝えない。テストで、**メッセージに入力の内容が含まれない**ことを確認する。
- **予防**: 「この例外のメッセージに、入力が含まれうるか」を、秘密を扱う箇所ごとに確認する。同じ理由で、エラー出力に値を含めない（13-4 の改行のエラーは、キー名だけ）。
- **この PR での例**: `tools/api-key/firebaseCliCredential.js` の `parseFirebaseCliConfig`、`tools/__tests__/firebaseCliCredential.test.ts`。

### 13-7. 他のツールの設定ファイルの場所を、環境を考えずに決める

- **重大度**: 低（環境によっては、動かない）
- **どういうときに起きるか**: 他のツール（`firebase` CLI）が保存した設定ファイルを、**決め打ちのパス**（`~/.config/configstore/firebase-tools.json`）で読むとき。
- **何が起きるか**: 環境変数 `XDG_CONFIG_HOME` を設定している人は、実際の保存先が違うため、「ログイン情報が見つかりません」となる。
- **原因（詳細）**: 自分のマシンの既定の場所だけを確認して、**元のツールがその場所をどう決めているか**（`configstore` は `XDG_CONFIG_HOME` を優先する）を確認していませんでした。
- **修正内容（汎用）**: 他のツールの保存先を読むときは、そのツールの**決め方に合わせる**。環境変数とホームディレクトリは、関数の**引数で受け取り**（`resolveFirebaseCliConfigPath(env, home)`）、テストで、「環境変数あり・なし・空文字」を確認する。
- **予防**: 他のツールの内部の仕様（保存先、形式、クライアント ID）に依存するときは、その依存が**壊れうること**を、コメントと docs に書く。
- **この PR での例**: `tools/api-key/firebaseCliCredential.js`、`tools/__tests__/firebaseCliCredential.test.ts`。

### 13-8. コマンドの引数が、効かないまま受け付けられる

- **重大度**: 中（安全のための指定が、黙って無視される）
- **どういうときに起きるか**: 複数のコマンドを持つ CLI で、**そのコマンドでは意味を持たないオプション**を指定したとき（`list --replace`、`revoke --env-file`、`users --email`）。
- **何が起きるか**: エラーにならず、指定が**無視されます**。`--replace` を付けて実行した人は、「入れ替わった」と思いますが、何も起きていません。`users --email a@b.c` は、指定したアカウントだけが出ると思って、全員の一覧を見ます。
- **原因（詳細）**: 1 章（入力の扱い）と同じ **fail-open** です。オプションの解釈を、コマンドと独立に行い、**コマンドとの組み合わせの検証**を持っていませんでした。また、コマンド名の一覧が、`parseArgs`（受け付ける）と `commands`（実行する）で**別々に定義**されていて、片方だけ追加すると食い違います。
- **修正内容（汎用）**:
  - 解釈のあとに、**コマンドごとに、意味のあるオプションだけを許す**検証（`assertCompatibleOptions`）を行い、合わないものは**エラー**にする。ヘルプの表示（コマンドなし）のときは、検査しない。
  - 重複している定義（コマンド名）は、**テストで一致を確認する**（`COMMAND_NAMES` と `COMMANDS`）。
- **予防**: 新しいオプション・コマンドを足したら、「どのコマンドで有効か」を、パーサーと、ヘルプ・docs の**両方**に反映する。
- **この PR での例**: `tools/api-key/parseArgs.js`、`tools/__tests__/parseArgs.test.ts`、`commands.test.ts`。

### 13-9. 宣言していない依存に頼り、失敗したときの案内が合わない

- **重大度**: 中（ある日、突然動かなくなり、案内の通りにしても直らない）
- **どういうときに起きるか**: ツールが、**自分では `package.json` に宣言していないパッケージ**（別のパッケージの依存の依存）を `require` しているとき。
- **何が起きるか**: 親のパッケージの更新、`--omit=optional` でのインストール、パッケージの巻き上げ（hoist）の違いで、**突然 `MODULE_NOT_FOUND`** になる。さらに、依存先のメジャーバージョンが、親が内部で使うものとずれると、**オプションが静かに壊れる**（例: 自分で作った `GoogleAuth` を、別バージョンの Firestore に渡す）。
- **原因（詳細）**: 「今のマシンでは動く」ことを、「依存として保証されている」ことと取り違えていました。推移的な依存は、**親の都合で変わります**。また、見つからないときの案内（「`npm ci` を実行してください」）が、**宣言されていない依存には効かない**（`npm ci` しても入らない）ため、案内そのものが誤解のもとになります。
- **修正内容（汎用）**:
  - 使うパッケージは、**自分で宣言する**（`@google-cloud/firestore`、`google-auth-library` を `devDependencies` に追加し、親が使うものと**同じメジャーバージョン**にする）。
  - `MODULE_NOT_FOUND` は、**どのパッケージが、どこで見つからなかったか**と、**直し方**（`firebase-functions` で `npm ci`）を示すエラーにする。それ以外の例外は、そのまま伝える。
- **予防**: `require` / `import` しているパッケージが、**自分の `package.json` にあるか**を確認する。ツールの依存が、本体と別のディレクトリにあるときは、docs に書く。
- **この PR での例**: `firebase-functions/package.json`、`tools/api-key/requireWithHint.js`、`initAdmin.mjs`。

### 13-10. docs の実行例と、実際の実行の仕方がずれる

- **重大度**: 低（意図しない場所にファイルができる）
- **どういうときに起きるか**: 相対パスを受け取るツールを、**`npm run` 経由**（作業ディレクトリが、リポジトリのルートになる）と、**`node ツール.mjs` の直接実行**（作業ディレクトリは、実行した場所）の両方で、実行できるとき。
- **何が起きるか**: docs が「相対パスは、リポジトリのルートからの位置」と書いていても、サブディレクトリから直接実行すると、**そこを基準**にファイルが作られる。管理外（Git の対象外とは限らない）の場所に、秘密のファイルができる。
- **原因（詳細）**: docs の記述を、**一番よく使う実行方法だけ**を前提に書き、**他の実行方法で、同じ説明が成り立つか**を確認していませんでした。
- **修正内容（汎用）**: 実行方法ごとに、**基準が何か**を、docs に書き分ける。事故が起きたときの影響が大きいもの（秘密のファイル）は、**書き込み先を明示**する。
- **予防**: 「実行の仕方が複数あるなら、その動作の違い」を、docs のレビュー項目にする（8 章の「利用者の視点」の一例）。
- **この PR での例**: `（非公開のエージェント API 仕様）` の `--env-file` の説明。

### 13-11. 見送った判断：他のツールの内部のクライアント ID を使う

- **判断**: 対応しない（受け入れた設計）
- **指摘**: `firebase login` のリフレッシュトークンを使うために、`firebase-tools` の内部に埋め込まれた OAuth のクライアント ID・シークレットを、そのパッケージのコードから読み込んでいる。内部の実装に依存しており、パッケージの更新で壊れうる。Windows のパスも想定していない。
- **理由**: 手動で設定を作る必要がなく、**`firebase login` だけで使える**ことが、このツールの目的に合っている。代替案（自前の OAuth の登録、サービスアカウントのキー）は、**秘密の管理が増える**。壊れたときは、`[redacted]` を付けず、アプリケーションのデフォルト認証情報で動かせる。Windows は、このリポジトリの対象外。
- **記録の仕方**: トリアージの基準（10-7）に照らして、**見送る理由と、壊れたときの代替**を書いておく。依存していること自体は、13-7・13-9 のとおり、コメントと docs に残す。
