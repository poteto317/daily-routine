# 画像リンクの有効期限と既存リンク失効の実装計画

[設計](../specs/2026-11-23-expiring-report-image-links-design.md) を実装する。参照した知見は L-017、L-029、L-921、L-1006。

1. Storage アダプターにテストを追加する。旧トークン全体を削除し、世代・メタ世代を照合して他の属性を保持する。再取得に失敗した場合やトークンが残った場合は署名しない。処理済みの画像は書き換えずに扱う。
2. Storage SDK の V4 GET 署名で同一世代に 15 分の有効期限を付ける。起票と AI は既存の経路を使用し、失敗は既存の画像スキップに統合する。カード本文と報告画面にリンクの期限を明記する。
3. 旧・新の画像プレフィックスを走査し、同じメタデータ処理を適用する CLI を用意する。対象プロジェクト名とバケット名を明示し、確認を既定、更新を明示指定にする。バケットのプロジェクト所属を実行前に管理画面または CLI で照合する。失敗を終了コードと件数で返し、URL・トークン・オブジェクト名を出力しない。
4. Jest で期限と対象世代、更新・再取得・署名失敗を確認する。Storage Emulator の合成画像で無署名の Firebase 直リンク拒否、旧トークン付き URL の移行前後、無関係なメタデータ・対象外オブジェクトの保持、確認モードの無変更を検証する。実際の Cloud Storage XML API で、無署名 GET が拒否され、署名付き GET が期限前後で許可・拒否されることは、デプロイ手順に検証環境での確認として記載する。全体テストと両ビルドを実行する。
5. 現行の運用文書と機能一覧に保護・移行・検証手順を反映する。変更を実装と運用文書の責務で分ける。
