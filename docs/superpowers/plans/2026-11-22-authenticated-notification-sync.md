# 通知同期の認証と保存先の実装計画

> 開発フローに沿い、実装前に回帰テストを追加する。

**目的** Firebase で本人確認した通知同期だけを受け付け、個人同期データから保存先を分離する。

**設計** [通知同期の認証と保存先](../specs/2026-11-22-authenticated-notification-sync-design.md)

## 作業

1. `firebase-functions/src/sync-helpers/` のテストを追加する。Bearer 欠落・認証失敗で保存しないこと、検証済み UID だけを渡すこと、別 UID の登録の更新を拒否すること、空配列と CORS を固定する。本文の通知項目を検証し、`storage.ts` のトランザクションと通知専用コレクションを実装する。スケジューラーが個人同期を参照しないことも確認する。
2. `src/features/routine/helpersSync.ts` と Firebase Messaging の既存ヘルパーを更新する。許可・Firebase Auth・ローカルスコープを確認後に ID トークンを付ける。セッション切り替え中は送信せず、所有者不一致の応答時だけ端末の FCM トークンを更新する。ログイン時は移行前から UID 固有のキーにあるスナップショットを読み、認証ガードは UID が変わると画面を再作成する。それぞれをテストする。専用 403 コードでの一度だけの再試行と、HTTPS・ループバックの許可とリダイレクトの拒否も確認する。
3. `syncRoutines`、`checkNotifications`、Web アプリの公開順序と再登録条件を運用文書に反映する。関連テスト、`npm run verify`、Firebase Functions のビルドを実行する。

## レビュー観点

- Firestore が別コレクションでも、既存登録の UID 更新を許さない。
- 認証主体はリクエスト本文に依存しない。別 UID の登録ではトランザクションに書き込みを追加しない。
- ログイン直後と競合時にも、別ユーザーのローカルデータを送信しない。
- SDK が未設定、通知が未許可、トークン取得が失敗した場合はネットワーク送信を行わない。
- 旧登録を使った通知が停止する範囲と再登録の手段を公開手順に示す。

- 同じ FCM トークンを異なる UID が同時に登録した場合、トランザクションの再試行後に所有者は一人に確定し、同 UID の再送と複数端末は成功する。
- 認証なしの OPTIONS は Authorization の許可を返し、検証処理と書き込みを呼ばない。
- キュー待機中に別 UID または同じ UID の新セッションになった場合は元の処理を送信しない。旧データのコピーに由来するルーティンは再ログイン後も起動時に送信しない。
