# アカウント管理者権限の実装計画

> 実装時はタスク単位でテストを先に書き、実装後に再実行する。

**目的** 一般利用者が管理者権限を自己付与できないようにし、管理画面の利用を確認済み管理者に限る。

**構成** プロフィールと権限を別のコレクションに保存する。役割変更の操作では Firestore バッチを使い、本人登録は存在確認と書き込みをトランザクションにまとめる。

**設計書** [管理者権限の設計](../specs/2026-11-22-account-admin-roles-design.md)

## タスク

1. `tools/firestore/account-admin.rules.test.mjs` で登録、他人へのアクセス、旧フラグ、権限の付与・剥奪、削除時の整合性を Firebase Emulator 上で確認する。失敗を確認して `firestore.rules` を修正する。
2. `accountService.mutations.test.ts` と `accountService.queries.test.ts` で登録、権限表示、管理者による更新を検証する。 `accountServiceCore.ts`、`accountServiceMutations.ts`、`accountServiceQueries.ts` の実装を変更する。ユーザー発行にはメモリ内永続化の一時 Firebase App を使用し、管理者画面の作成成功後は一覧を更新する。編集開始時から役割が変わった場合だけ権限を更新する。
3. 設定チェックリストと参照文書に、Firestore の対象環境を確認できない場合の公開保留、既存権限の棚卸し、承認済み UID の初期付与、公開後の確認を記載する。Firebase Emulator と `npm run verify` を実行する。

## 確認する条件

- 未認証、未登録、匿名、通常、旧フラグ付きユーザーの権限が混ざらない。
- 一括更新でも本人だけで権限を得られず、許可された付与と剥奪が反映される。
- プロフィールの作成・削除と権限の更新が一致する。
- 自動登録は別端末または管理者が作成済みのレコードに対して書き込まない。
- 既存の `isAdmin: true` は棚卸しの候補として扱い、認可には使用しない。

責務は、アカウント認可と対応する実装・テスト、および移行手順の二つに分ける。

## 検証の合格条件

- 本人による `false` 付き作成は許可し、`true`、型違い、欠落、他人 UID の作成と一般利用者の更新を拒否する。旧フラグのみの利用者は一覧、他人の読み書き、権限付与を拒否する。
- 確認済み管理者による付与、剥奪の直後に対象のアクセスが切り替わる。プロフィールなしの付与と権限付きプロフィールだけの削除は拒否し、正しいバッチは許可する。
- プロフィール内の UID と旧フラグが一覧の UID と役割に混入しない。新規ユーザー発行で主 Auth が切り替わらない。プロフィール保存失敗は呼び出し元に伝え、初回本人登録と後からの付与で復旧できる。
- 本番管理者候補を承認済み UID と照合し、結果を個人情報を含まない形で作業記録に残す。アクセス不能の場合は未確認とし、公開保留を記録する。

- 本人は未作成のものを含めて自分の権限レコードを取得できる。他人の取得と一覧は確認済み管理者だけに許可する。
- 登録トランザクションの再試行で先に保存されたプロフィールを上書きしないことを確認する。
