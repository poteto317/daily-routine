# 不具合報告の処理上限の実装計画

設計は [不具合報告の処理上限](../specs/2026-11-22-bug-report-quotas-design.md) に従う。

1. トランザクションのテストを先に追加する。各上限で枠超過時にどちらも加算しないこと、期限切れロックの再取得で両方を加算すること、重複時に加算しないことを確認する。UTC 日付とプロジェクトの切り替え、拒否済み報告の翌日スキップ、無効なカウンターと設定も検証する。トリガー経由で 0 または上限到達時に画像取得・AI 整形・起票をそれぞれ呼ばないことも確認する。
2. 報告の再読込と処理ロックを小さなモジュールへ移し、起票先と UTC 日付でプロジェクトカウンターを、報告者 UID のハッシュで利用者カウンターを参照する。両方の読み取りが済んでから、カウンターとロックを同時に書き込む。報告者 UID は保存済みの報告から取得する。
3. トリガーに Firebase の文字列パラメータ `BUG_REPORT_USER_DAILY_LIMIT`（既定値 `5`）と `BUG_REPORT_PROJECT_DAILY_LIMIT`（既定値 `50`）を接続し、10 進の非負安全整数として厳密に検証する。既存の `claimProcessing` で処理への入口を制御する。上限到達時のエラーコードをサーバー側の報告型に追加する。
4. 対象テスト、全体の検証コマンド、Functions のビルドを実行する。Firestore Emulator でも、同じプロジェクトの最後の枠を争う同時実行で確保が 1 件に収まることを確かめる。
