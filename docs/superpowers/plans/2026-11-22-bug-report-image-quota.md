# 報告画像の容量制限の実装計画

[設計](../specs/2026-11-22-bug-report-image-quota-design.md) に従い、サーバー、ブラウザ、セキュリティルールを接続する。

1. Functions に入力検証と予約のテストを書く。Firebase UID を採用し、画像は base64 の長さをデコード前に検査し、実バイト数と既存の形式判定で検証する。UID・件数・容量を利用者と全体のカウンターへ同時に加算し、画像の保存前に予約を記録する。一意の報告 ID と既存の画像参照形式を利用し、画像は旧ルールで拒否される独立したトップレベルの名前空間に保存する。起票処理は旧・新の保存先を厳密に照合する。
2. callable で予約済みのパスに世代条件付きで画像を保存し、期限内の予約と報告ドキュメントをトランザクションで確定する。途中エラー後の予約は期限まで保持する。回収は予定時刻で検索し、状態をトランザクションで回収中にした後、Storage の削除と別のトランザクションで枠を返却する。失敗した予約の再試行を後ろへ移す。作成イベントは新方式のパスのみ照合し、遅れて確定したオブジェクトの世代を指定して削除する。
3. 画像付き送信を Firebase callable に接続し、画像なしの送信は既存の Firestore 経路を通す。容量不足と保管期間をフォームで案内する。Storage の直接書き込みとクライアントからの画像付き Firestore 作成を禁止する。
4. 利用者と全体の件数・バイト上限、実バイト判定、途中失敗と無通信での期限切れ、提出・回収の競合、削除の失敗と再試行、旧パスの互換性を Jest で確認する。ローカルの Firebase Emulator で実 SDK による同時予約、認証済みクライアントの直接 Storage 書き込み・画像付き Firestore 作成の拒否、画像なし Firestore 作成、callable の画像付き送信で予約が確定すること、期限切れ回収を確認する。全体テスト、アプリと Functions のビルドを実行する。
5. 切り替え手順と保管・上限の仕様を運用文書に追記する。実装・テストと運用・設計文書の責務でコミットを分ける。

参照した知見は L-002、L-003、L-004、L-464、L-862、L-956、L-1006。
