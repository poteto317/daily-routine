# アカウント管理者権限の設計

カード #20 の要件は、本人登録を一般権限に固定し、確認済みの管理者だけが昇格を行えるようにすること。既存の管理者候補を棚卸しし、一般利用者の権限が上がらないことを Firestore Emulator で検証する。

## 認可と既存データ

- Firestore の管理者判定には `accountAdminGrants/{uid}` の存在を使う。移行前のルールではこのコレクションへのクライアント書き込みは全面拒否され、既存プロフィールの `isAdmin` は移行候補の調査に使う。
- 本人による初回プロフィール作成は `isAdmin: false` の場合に許可する。存在確認と作成はトランザクションで行い、既存プロフィールは上書きしない。本人以外の作成、一覧、他人の読み取り、更新・削除には確認済み管理者の権限を要する。
- 権限レコードは確認済み管理者が他人に付与・剥奪できる。操作主体の権限はコミット前の状態で判定する。付与にはコミット後に対象プロフィールが必要。プロフィール削除時は同じバッチで権限も解消する。本人の権限変更を禁止する既存画面の制約をルールでも適用する。
- 一覧の管理者表示と画面へのアクセス判定は権限レコードを参照し、プロフィールに入った UID や役割よりも実際のドキュメント ID と権限レコードを優先する。登録ではプロフィールと付与を一括保存し、新規 Firebase ユーザーを発行しても操作中の管理者セッションを保持する。Auth 作成後にプロフィールの保存結果を確認できなければ成功表示を出さない。保存済みかを一覧で再取得し、未作成ならユーザー本人の初回ログインで一般プロフィールを作り、確認済み管理者が一覧から必要な権限を付与する。

## 運用

最初の管理者は Firebase の IAM 権限を持つ運用者が、Firebase Authentication と承認済み担当者一覧を突き合わせた UID にだけ付与する。既存の `isAdmin: true` は過去の自動付与を含むため、自動移行は行わない。対象環境の棚卸し、初期付与、ルール公開、アプリ公開の順序を運用手順に記載する。対象環境、作業権限、承認済み UID を確認できるまで、初期付与とルール公開を保留する。

L-021 と L-862 に従い、権限の書き込み条件と登録の競合をルールとテストで確かめる。
