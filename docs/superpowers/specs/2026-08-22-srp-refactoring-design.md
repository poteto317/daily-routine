# 単一責任リファクタリング 設計

## 目的

本番コードを変更理由ごとの小さなモジュールへ整理し、各ファイル・関数・コンポーネントが一つの責務だけを持つ状態にする。振る舞い、公開API、保存形式、画面表示は原則として変更しない。

監査、責務分割、検証、再監査を繰り返し、全体監査で新しい単一責任違反が見つからなくなった時点で完了とする。各反復を1ループとして数え、実施内容と結果を記録する。

## 対象範囲

- `src/` の本番TypeScript・JavaScriptコード
- `firebase-functions/src/` の本番コード
- `tools/` の保守対象スクリプト

以下は、行数が多いだけでは監査対象にしない。

- テスト、テストfixture、Storybook story、E2E
- ロケール、静的データ、テストケース定義
- ビルド生成物と外部依存
- 一つの目的に沿って並ぶ宣言的な設定・マッピング

これらにも独立した変更理由が混在している場合は対象へ戻す。

## 単一責任の判定

ファイルサイズや公開関数数は候補抽出のシグナルとして使い、それだけで違反とは判定しない。次のいずれかを満たす場合に分割対象とする。

- 独立して変更される理由を二つ以上説明できる
- UI表示、状態遷移、永続化、外部I/O、ドメイン計算の複数層を同時に扱う
- 異なる利用者・画面・機能向けの処理が同じ汎用 `helpers` に集約されている
- 一部だけを理解・テスト・再利用するために無関係な実装まで読む必要がある
- ある責務の変更が、別責務の依存やテストを不必要に巻き込む

候補抽出では次を優先する。

- 120行を超える本番コード
- 公開関数が6個を超えるファイル
- 三つ以上の独立したセクションを持つファイル
- コンポーネント内に表示以外の変換、計算、永続化が混在する箇所

## 採用アプローチ

責務クラスタ単位で抽出する。機械的な行数分割やディレクトリ全面再編は行わない。

各クラスタについて次を実施する。

1. 現在の利用箇所、テスト、公開APIを確認する。
2. ファイルが持つ変更理由を列挙する。
3. 一つの変更理由だけを持つモジュールへ処理を移す。
4. 既存のimport経路が公開APIの場合は、元ファイルから再エクスポートして互換性を維持する。
5. 循環依存を避け、下位の純粋ロジックから上位の組み立て処理へ一方向に依存させる。

小さくても同じ変更理由で常に一緒に変更される定数・型・関数は分断しない。分割後のファイル数を増やすことではなく、変更理由を一つにすることを優先する。

## モジュール境界

原則として、次の責務を別モジュールにする。

- 日付・識別子・値の正規化
- ドメイン計算と集計
- 状態遷移とmutation
- LocalStorage、Firestore、HTTPなどのI/O
- React hookによるライフサイクルと依存の組み立て
- JSXによる表示
- 文言・表示用class・表示モデルの生成

機能内で閉じる処理は、その機能ディレクトリ内に置く。複数機能で本当に共有される純粋処理だけを `src/lib/` へ置く。

## 監査ループ

各ループを次の順序で行う。

1. **全体監査**
   - 行数、公開関数数、セクション数から候補を抽出する。
   - import、利用箇所、テストを読んで変更理由を判定する。
2. **対象選定**
   - 責務境界が明確な候補を優先する。
   - 一度に扱うのは、相互に関連する一つの責務クラスタとする。
3. **保護テスト**
   - 既存テストで外部動作が保護されていることを確認する。
   - 保護されていない振る舞いがあれば、実装変更前に失敗するテストを追加する。
4. **責務分割**
   - 振る舞いを変えずに抽出し、必要な再エクスポートを残す。
5. **検証**
   - 対象テスト、型検査を実行する。
   - コード変更後は必ず `npm run verify` を実行する。
6. **再監査**
   - 分割先と依存元を再確認する。
   - 新たな責務混在がなければループを完了し、回数を1増やす。

ループ記録には、回数、監査候補、分割した責務、変更ファイル、対象テスト、`npm run verify` の結果を含める。

## 終了条件

次の全条件を満たした全体監査を、最終ループとする。

- 判定基準に該当する未対応のSRP違反が0件
- 分割で新しい循環依存や責務混在を作っていない
- 公開APIと利用側の振る舞いを維持している
- 作業ツリー内の対象テストが成功する
- `npm run verify` が成功する

行数や関数数の閾値を超えていても、単一の宣言的データ、単一アルゴリズム、単一コンポーネントとして一つの変更理由しか持たない場合は、理由を記録して完了対象から除外できる。

## テスト戦略

- 純粋関数の抽出では、既存の入力・出力契約を対象テストで維持する。
- 状態遷移の抽出では、成功、失敗、境界値を公開動作から検証する。
- Reactコンポーネントの分割では、表示、操作、ARIAをReact Testing Libraryで検証する。
- I/O境界の分割では、外部依存だけをmockし、データ変換と状態更新は実コードで検証する。
- 各ループで対象テストと `npm run verify` を実行する。
- 最終ループでは、全体監査結果とフル検証結果を併せて確認する。

## リスク管理

- 保存形式、同期payload、URL、画面文言は変更しない。
- 新しい依存パッケージは追加しない。
- 公開import経路の一括変更は避け、必要に応じて互換レイヤーを残す。
- リファクタリングと機能追加・バグ修正を同じ差分に混在させない。
- 既存の未コミット変更が見つかった場合は上書きしない。
- コミットとpushは、ユーザーから明示的な指示がない限り実行しない。

## 初期監査で確認した候補

- `src/features/statistics/statistics/weeklyGoals.ts`
  - 日付計算、目標定義の復元、完了索引、ストリーク計算、全体組み立てが混在する。
- `src/hooks/headerMenuItemHelpers.ts`
  - Todo動的項目生成、静的項目の権限制御、並び順決定が混在する。
- `src/features/routine/components/helpers.ts`
  - カード、フォーム各部、時間競合、表示classと文言が混在する。
- `src/features/work-tracker/page/helpers.ts`
  - 履歴表示、テンプレート入力、タイマー、サマリー、インサイト生成が混在する。

これらを確定対象とはせず、各ループの利用箇所調査で責務境界を再確認してから変更する。
