# 報告画像の容量制限と回収

画像付き報告を Firebase Authentication 付きの callable 関数で受け付ける。サーバーが本人の UID、入力本文と環境情報、画像の実バイト数と形式を検証する。画像は従来どおり 1 報告につき 3 枚、1 枚 5 MiB までとする。画像なしの既存 Firestore 送信は継続できる。

## 保存と回収

- 画像の保存前に Firestore トランザクションで利用者別と全体の画像枠を確保し、報告 ID と画像の保存先を記録する。初期上限は利用者あたり 20 枚・50 MiB、全体で 1,000 枚・2 GiB。予約中と提出済みの画像を含む。クライアントから Storage への直接書き込みを拒否する。
- サーバーが予約済みパスに画像を新規作成し、画像参照を含む報告を Firestore に作成する。報告の作成と提出済みへの変更は、期限内で回収中でもない予約を再確認した同じトランザクションで行う。クライアントから画像付きの報告を直接作成できない。
- 予約は 1 時間、提出済みの画像は 30 日間保管する。15 分ごとの回収は予約の現在の状態と期限をトランザクションで確認し、回収中へ遷移させてから記録済みパスを削除する。全パスを削除または不存在と確認できた後に、予約の削除と枠の返却を同時に行う。失敗した回収は枠を保持して再試行する。報告本文と起票内容は残り、画像のリンクは画像回収後に開けなくなる。保管期間と枠不足時に画像を外して再送できることを報告フォームで案内する。
- 新規画像には旧ルールが許可していない `bugReportManagedImages/` の名前空間を使う。Storage の作成イベントは予約とパスを照合し、予約が存在しない、回収中、または記録にないパスの場合にイベントの世代を指定して削除する。期限のみが過ぎた場合はスケジュール回収で状態を確定してから削除する。一時的な照合・削除エラーはイベント配信を再試行する。既存の報告・画像は読み取り互換を維持し、既存データの削除やバケットの保存設定の変更を伴わない。
- 上限は予約中・提出済みの管理枠に適用する。遅れて確定したオブジェクトは作成イベントで回収するまで一時的に残り得る。Cloud Storage のソフトデリートやバージョニング、既存画像は別途バケット設定に従う。

## 切り替え

Storage トリガーと既定バケットのリージョン互換を確認する。両方の画像パスに対応した起票関数、新規の受付・回収関数、新しい Web クライアント、Firestore と Storage のルールの順に公開する。ルールの切り替え後は旧クライアントの画像付き送信が失敗するため、新しいクライアントを利用できる状態で実施する。
